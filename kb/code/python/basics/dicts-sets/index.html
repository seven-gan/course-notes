    这一页解决一个问题：把「按下标找」换成「按名字找」和「按归属找」。

    前面几页的容器只有一个入口 —— 下标。取第 3 个元素很方便，但想要「编号 A-001 的记录」「出现 3 次以上的词」「两批文件的差异」时，下标完全帮不上忙：只能从头扫到尾逐个比对。

    现实问题几乎都是后一种形状。字典（dict）负责「用一个名字换到一份数据」，集合（set）负责「只关心有没有、归不归一类」。二者内部都靠哈希表（hash table）实现，查找速度几乎不受数据量影响。

    这一页学完，你将能够：

    能力 具体表现
    按名字取数 用 d[k]、get、setdefault 各司其职，不再靠遍历
    增删改查 记住 pop / popitem / del / update / clear 的差别
    遍历得体 分清遍历键、遍历值、遍历键值对，会用 items() 解包
    分组与计数 用 Counter 数词频，用 defaultdict 把数据分堆
    查得快 明白为什么 in 在集合上比在列表上快成千上万倍
    打印集合 知道集合顺序不可依赖，一律 sorted() 后再输出

    这一页的主线

    本页的骨架是两个新入口：字典按名字取数，集合按「在不在」取数。

    第二到八节把字典讲透（方法、遍历、Counter、顺序、合并），第九节起讲集合， 第十节回到两者的共同底座 —— 哈希。字典部分篇幅最长，读完可以先放下集合。

    这页的重点

    三个最容易搞错的地方，先点出来：

    1. 空集合不是 {}，而是 set() —— {} 是空字典，写错不报错，直到用 add 才炸
    2. d[k] 与 d.get(k) 不是一回事：前者取不到抛 KeyError，后者给默认值。「键可能不存在」用 get，「不存在就是 bug」用 d[k]
    3. 集合打印顺序不可依赖，尤其字符串集合，每次运行都可能不同；要固定就 sorted(集合)

相加（次数累加）: Counter({'b': 4, 'a': 3})
相减（结果非正的元素被丢掉）: Counter({'b': 2, 'a': 1})
交集（取较小的次数）: Counter({'a': 1, 'b': 1})
并集（取较大的次数）: Counter({'b': 3, 'a': 2})

    加减法的语义与集合运算很像，但作用在「次数」上：

    运算 每个元素的结果 适合
    a + b 次数相加 把两批数据合并统计 ✓
    a - b 次数相减，≤ 0 的不保留 从统计里挖掉一部分
    a & b 取较小的次数 「两边都出现过的量」
    a \| b 取较大的次数 「两边的上限」

    注意 - 会丢掉结果非正的元素，这与普通数学减法不同 ⚠

    七、字典的顺序：插入顺序，不是自动排序¶

    7.1 它记住的是「你写进来的顺序」¶

    从 Python 3.7 起，字典保证按插入顺序保存键。注意：它有序，但顺序来自「你插入的先后」，不是「按大小排好」。

     1
 2
 3

    d = {"b": 1, "a": 2, "c": 3}

    操作 位置会变吗
    改某个已有键的值 不变 ✓
    删掉一个键，再重新加 排到最后 ⚠
    用已有的键赋新值 不变 ✓

    7.2 「有序」不等于「排过序」¶

    有序说的是「顺序确定、可预期」，不是说「按字母或数字排好了」：

    1

    sorted() 不会改原字典，它返回一个新列表：

    写法 返回 原字典
    sorted(d) 键的列表 不动 ✓
    sorted(d.items()) (键, 值) 的列表 不动 ✓
    sorted(d.values()) 值的列表 不动 ✓
    dict(sorted(d.items())) 新的、按 key 排好的字典 不动 ✓

    要「排好序的字典」，就得自己把 sorted 的结果再 dict(...) 一次

    需求 做法
    只要结果稳定可复现 sorted(d) ✓ 够用
    要拼音顺序 sorted(d, key=lambda k: 拼音(k))，自己提供拼音

    7.4 按 value 排序¶

    按值排序要多写 key=：sorted 默认比「元素本身」，而 d.items() 的元素是 (键, 值) 元组 —— 默认先按键比，那不是我们要的。

    1
2
3
4
5
6

print("从低到高:", by_score)
print("转回字典:", dict(by_score))
print("从高到低:", sorted(scores.items(), key=lambda kv: kv[1], reverse=True))

    从低到高: [('小华', 79), ('小美', 88), ('小刚', 95)]
转回字典: {'小华': 79, '小美': 88, '小刚': 95}
从高到低: [('小刚', 95), ('小美', 88), ('小华', 79)]

    key=lambda kv: kv[1] 的意思是「拿元组第 2 项（值）来比」。换成 kv[0] 就是按键比，而按键比本来就是默认行为

    7.5 多级排序：同分怎么办¶

    sorted 是稳定排序，同分元素会保持原顺序。但「原顺序」是插入顺序，往往不是你要的。想让同分的按名字排，就让 key 返回一个元组：

    1
2
3
4
    score = {"bob": 88, "alice": 95, "carol": 88}

print("只按分数:", sorted(score.items(), key=lambda kv: kv[1]))
print("分数降序、同分按名字:", sorted(score.items(), key=lambda kv: (-kv[1], kv[0])))

    只按分数: [('bob', 88), ('carol', 88), ('alice', 95)]
分数降序、同分按名字: [('alice', 95), ('bob', 88), ('carol', 88)]

    元组比较的规则是「先比第一项，相等再比第二项」，所以 (-kv[1], kv[0]) 就实现了「分数从高到低，同分按名字从 A 到 Z」；想让某项降序，就在它前面加负号（对数字有效，字符串不行）。

    7.6 不用 lambda 的两种干净写法¶

    1

    itemgetter 写法: [('bob', 88), ('carol', 88), ('alice', 95)]

    写法 可读性 适合
    key=lambda kv: kv[1] 一看就懂 ✓ 表达式简单时首选
    key=itemgetter(1) 更快、更短 取固定第几项时
    key=score.get 最短 ✓ 只需要「按键的值排序」
    key=lambda kv: (-kv[1], kv[0]) 略长 多级排序只能这样写

    判断依据：取第几项用 itemgetter； 要算表达式（取负、拼接、切片）就用 lambda

    八、字典合并的三种写法¶

    写法 结果放在哪 原字典 版本要求
    d.update(别的) 改 d 自己（就地） 被改 ⚠ 一直都有
    d1 \| d2 返回新字典 都不动 ✓ Python 3.9+
    d1 \|= d2 改 d1（就地） d1 被改 ⚠ Python 3.10+
    {**d1, **d2} 返回新字典 都不动 ✓ Python 3.5+

    三者的合并规则完全一样：右边的覆盖左边。

    场景 用 原因
    想把结果存进新字典，旧的不动 a \| b ✓ 一眼看出「不改原件」
    想就地更新（尤其在循环里累积） a.update(b) 目的明确
    要在字面量里合并 {**a, **b, "k": v} ✓ 只有解包能这么写

    十、哈希原理：为什么它这么快¶

    前面反复说「哈希表查找几乎与数据量无关」，这一节说清为什么。

    10.1 一句话版本¶

    字典和集合先用「哈希函数」把键换算成整数（指纹），再用它直接算出「该放第几格」，所以查找时不用逐个比对，一次跳到那格。

    打个比方：列表像一排没编号的箱子，找东西只能从头翻；字典像带索引的档案柜，先算出「该去第 3 排第 7 格」，直接走过去拿

    10.4 复杂度：为什么查询几乎不随数据量变慢¶

    操作 列表 字典 / 集合
    按下标取 lst[i] O(1) ✓ 没有下标
    按键取 d[k] 没有键 O(1) 平均 ✓
    判断 x in 容器 O(n) —— 要一个个比 ⚠ O(1) 平均 ✓
    插入 / 追加 append 是 O(1) O(1) 平均 ✓
    删除指定元素 O(n) —— 后面元素要前移 O(1) 平均 ✓
    按顺序遍历 O(n) O(n)

    「平均 O(1)」的含义：不管字典里有 10 个还是 1000 万个键， d[k] 花的时间基本一样。这就是它相对列表的根本优势。

    O(1) 有个前提：哈希要「散得开」

    如果所有键的哈希值都挤在少数几格上（叫「哈希冲突」），格子里的元素还是要逐个比，速度就会退化。所以有两个实际影响：

    影响 说明
    字符串键要哈希随机化 防止有人构造「全部撞一起」的输入来拖垮服务
    哈希随机化让字符串集合的顺序每次不同 这正是下一节的问题 ⚠

    结论：O(1) 是「平均情况」的保证，对普通数据（数字、短字符串）完全成立，可放心依赖

    十一、集合的遍历顺序是不稳定的¶

    这是本页第三个必须背下来的点。

    容器 打印顺序稳定吗 说明
    列表 稳定 ✓ 就是你的插入顺序
    元组 稳定 ✓ 同上
    字典 稳定 ✓ 插入顺序（3.7+ 保证）
    集合 不稳定 ⚠ 顺序由哈希值决定

    从「哈希值必须始终不变」出发想。再想：元组不可变，那「元组里的元素」不可变吗？

    核心原因：字典靠哈希值定位。 如果键的内容能被改，哈希值就变了， 字典就再也找不到它 —— 所以 Python 禁止可变对象当键。

    1
2
3
    # @expect-error
d = {}
d[[1, 2]] = "列表当键"

    TypeError: unhashable type: 'list'

    报错说 unhashable type: 'list'： 「不可哈希的类型：列表」。

    元组可以，因为它创建后内容不能改：

    1
2
3
4
    grid = {(0, 0): "起点", (1, 2): "终点"}
print("用元组当键:", grid[(1, 2)])
print("查不存在的坐标:", grid.get((9, 9), "空地"))
print("所有坐标按序:", sorted(grid))

    用元组当键: 终点
查不存在的坐标: 空地
所有坐标按序: [(0, 0), (1, 2)]

    但「元组里套列表」不行 —— 元组本身不可变，可里面的列表照样能 append：

    1
2
    # @expect-error
d = {([1, 2], 3): "元组里含列表"}

    TypeError: unhashable type: 'list'

    报的是同一个错：unhashable type: 'list'

    当键的写法 可以吗 原因
    (1, 2) 可以 ✓ 全是不可变元素
    ([1], 2) 不行 ✗ 里面有条列表
    "abc" 可以 ✓ 字符串不可变
    [1, 2] 不行 ✗ 列表可变
    frozenset({1, 2}) 可以 ✓ 它是不可变的集合

    判断依据：想用「一组值」当键，就用不可变的东西包起来 ——元组、字符串、数字、frozenset，绝不能出现列表 / 集合 / 字典 ✓

    小结¶

    要记住的 为什么
    字典 = 键 → 值的映射 入口是「叫什么」，不是「第几个」
    键必须唯一、必须可哈希 键要用来定位，内容不能变
    值可以是任何东西 一个键挂列表、挂字典都行
    d[k] 缺键报错，get 不报错 「缺了算正常」用 get
    get 不改字典，setdefault 会写 差别就在这一件事上
    分组必须用 setdefault / defaultdict 用 get 会静默丢数据 ✗
    in d 只判断键 判断值要写 d.values()
    三种遍历：键 / values() / items() for k, v in d.items() 最常用
    for x in d 拿到的是键 期待值就会出错，且不报错 ⚠
    遍历时增删键会 RuntimeError 改成遍历 list(d) 这份快照
    字典保持插入顺序，不是自动排序 3.7+ 的保证；要排序得自己 sorted
    update / \| / \|= 都是「右覆盖左」 合并配置时高优先级放右边
    \| 是浅合并 嵌套字典会被整体替换
    空集合是 set()，不是 {} {} 是空字典 ⚠
    remove 报错，discard 不报 与 d[k] / get 的选择同构
    去重保序用 dict.fromkeys set 会丢顺序
    集合运算 \| & - ^ 「筛人」「找差异」写成一行
    ^ 是「恰好一边有」 两边都有的会被排除
    1 1.0 True 是同一个键 哈希相同就视为相同
    可变对象不能当键 指纹会失效；用 tuple / frozenset
    查找接近 O(1) 哈希一次定位，与数据量基本无关
    集合打印顺序不稳定 字符串哈希随机化，一律 sorted()
    要在循环里反复 in 查询 先把那列数据变成集合
    Counter 取缺键返回 0 计数场景最省事，还白送 most_common
