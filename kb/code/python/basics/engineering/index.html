    14 工程习惯¶

    这一页解决一个问题：让代码能被人读懂、能被改动、能被交付。

    前面十三页教你「把程序写出来」。这一页教的是另一类能力 —— 让写出来的程序三个月后还看得懂、别人接手还能改、改了以后知道自己有没有改坏。

    能力 具体表现 靠什么
    可读 扫一眼就知道每个名字是什么 命名规范
    可懂 知道这段代码「为什么这么写」 注释讲意图、docstring 讲契约
    可查 编辑器能提示、能自动查错 类型标注
    一致 换个人写，读起来像同一个人写的 统一格式 + 自动格式化
    可验 改完立刻知道有没有弄坏 单元测试
    可交付 别人拿到文件夹能跑起来 项目结构 + 依赖清单
    可追 出了问题能查到当时发生了什么 logging 而不是 print

    这页的重点

    工程习惯的核心只有一句话：写代码时，把「未来的自己」当成读者。

    未来的自己有三个特点：不记得当时的思路、看不出省略的细节、不敢乱改。 所以：

    1. 名字要能自解释 —— 而不是靠注释补充说明
    2. 注释要讲「为什么」 —— 「做什么」代码自己会说
    3. 测试要能自动跑 —— 而不是「我记得我试过」

    最容易搞错的一条：类型标注不会在运行时检查。 写错类型照样能跑，它换来的是编辑器和静态检查工具的帮助。

    1.2 三个真实的翻车场景¶

    工程习惯不是「好看」，它挡的是这三类事故：

    场景 表现 根因 本页的解法
    无人敢改 改一行要通读三百行 命名含糊、函数过长 命名规范、拆分函数
    悄悄改坏 改完程序照跑，结果错了 没有测试 单元测试 + 浮点比较
    无法复现 出问题时已经看不到现场 用 print 输出，一闪而过 logging 写进文件

    第三类最阴险：print 的内容滚动几屏就找不到了， 而 logging 会把每一次警告、每一次错误留下证据

    二、命名规范（PEP 8）¶

    2.1 PEP 8 是什么¶

    PEP 8 是 Python 官方的代码风格指南，它不是语法规定， 而是「整个 Python 社区默认这么写」的约定。

    为什么值得遵守：因为 Python 代码在真实项目里是混着读的 —— 读你用的第三方库、读同事写的模块、读三个月前自己写的文件。 风格统一，读起来就不需要「切换大脑」。

    PEP 8 对命名的规定可以压缩成一张表：

    对象 风格 例子 常见反例
    变量 snake_case（小写下划线） total_price totalPrice
    函数 / 方法 snake_case read_sensor ReadSensor
    类 CamelCase（大驼峰） SensorReading sensor_reading
    常量 UPPER_CASE（全大写下划线） MAX_RETRY maxRetry
    内部 / 私有 前置一个下划线 _default_timeout default_timeout
    模块 / 包 全小写，尽量不用下划线 dataio DataIO
    「不关心」的占位 单个下划线 for _ in range(3) for unused in ...

    # ---------- 常量：全大写 + 下划线，写在模块顶部 ----------
MAX_RETRY = 3
DEFAULT_TIMEOUT_SECONDS = 5.0

# ---------- 内部使用：前置一个下划线表示「别在外部依赖它」 ----------
_cache = {}


# ---------- 类：大驼峰 ----------
class SensorReading:
    """一条传感器读数。"""

    def __init__(self, value):
        self.value = value

    # ---------- 方法：小写下划线 ----------
    def scaled_by(self, factor):
        """按比例放大读数。"""
        return self.value * factor


# ---------- 函数：小写下划线，名字是「动词 + 名词」 ----------
def read_sensor(sensor_id):
    """读取一个传感器的原始值。"""
    return {"sensor_id": sensor_id, "value": 25.4}


reading = SensorReading(25.4)

print("常量:", MAX_RETRY, "| 内部值:", DEFAULT_TIMEOUT_SECONDS)
print("方法调用:", reading.scaled_by(2))
print("函数调用:", read_sensor("A-001")["value"])

方法调用: 50.8
函数调用: 25.4

    前置下划线到底是什么意思：

    写法 含义 谁来遵守
    name 公开的，可以被外部使用 ——
    _name 内部实现细节，外部别依赖 靠约定，Python 不强制
    __name 类内部触发「名字改写」，避免被子类覆盖 语言机制

    注意 _name 不是「私有」 —— 它只是一句约定： 「这是我内部用的，哪天我改了不通知你」 用 import 导进来照样能用，只是不礼貌。

    class Counter:

    三、注释与文档字符串¶

    3.1 注释讲「为什么」，不讲「做什么」¶

    代码自己会说明「做什么」（只要你命名得好）， 注释唯一不可替代的作用是：记录代码里没有的信息。

    那到底是哪些信息？主要是三类：

    注释该写的内容 例子
    为什么这么写（业务规则、约定） 「结算系统按分入账，故此处必须四舍五入到 2 位」
    为什么不那样写（避开的坑） 「不能用除法，除数为 0 时业务上要返回 0」
    来源与约束（出处、限制） 「阈值来自合同附录 B，改动需同步通知对账」
    注释不该写的 为什么 改法
    「把 x 加 1」 代码已经写了 x += 1 删掉
    「循环遍历列表」 同上 删掉
    「这里先这样，以后再改」 没有信息量 写成待办事项或直接改
    「上面这行是错的，正确的在下面」 注释会在代码改动后过期 删掉旧代码，让注释跟着代码走 ⚠

    def summarize(readings):
    """把一组读数取平均，并统计超过阈值的条数。"""
    threshold = sum(readings) / len(readings)
    over = sum(1 for r in readings if r > threshold)
    return threshold, over


def summarize_changed(readings):
    """有人把「严格大于」改成了「大于等于」—— 只差一个字符。"""
    threshold = sum(readings) / len(readings)
    over = sum(1 for r in readings if r >= threshold)
    return threshold, over

    保险 怎么做
    看有没有真跑 用 -v 参数，会打印每条用例的名字 ✓

    def running_mean(values):
    """返回「累加平均值」列表。

    例: [1, 2, 3] → [1.0, 1.5, 2.0]
    """
    result = []
    total = 0.0
    for count, value in enumerate(values, start=1):
        total += value
        result.append(total / count)
    return result


# ---------- 四个测试：正常、边界、极端、浮点 ----------
def test_empty():
    """边界：空输入应当返回空列表。"""
    assert running_mean([]) == []


def test_single():
    """边界：只有一个元素时平均值就是它自己。"""
    assert running_mean([5]) == [5.0]


def test_three_values():
    """正常：用能心算的数据核对。"""
    assert running_mean([1, 2, 3]) == [1.0, 1.5, 2.0]


def test_float_uses_tolerance():
    """浮点：必须用 isclose，不能用 ==。"""
    import math
    got = running_mean([0.1, 0.2])[1]
    assert math.isclose(got, 0.15, abs_tol=1e-12)

def classify(root):
    """粗判一个目录是「脚本」还是「项目」。"""
    root = Path(root)

        (root / "tests").is_dir(),
        (root / "README.md").is_file(),

    7.3 目录命名与分层惯例¶

    目录名 放什么 说明
    src/ 或 <包名>/ 真正的源码 放在 src/ 下能避免「测试时导入了别处的同名模块」
    tests/ 测试 与 src/ 平级
    data/ 输入数据 大文件通常不进版本库
    out/ 或 outputs/ 结果输出 能重新生成的东西不进版本库 ✓
    scripts/ 一次性脚本 处理数据、生成报表
    docs/ 文档 与代码分开
    notebooks/ 探索性实验 适合做分析，不适合当最终代码

    一条容易忽视的规则：「能重新生成的东西」和「源头」要分开放。

    类别 例子 处理
    源头 源码、配置、说明文档 进版本库 ✓
    中间产物 缓存、日志 忽略
    结果 图、报表、导出文件 一般忽略 ✓

    这样做的直接好处：目录里永远只有一个「真相来源」—— 结果不对时，一定是代码或数据的问题，不可能是「有人手改了输出文件」 ✓

    八、用 logging 代替 print¶

    8.1 为什么 print 不够用¶

    print 是排查问题最直接的工具，但它有四个绕不过去的短板：

    问题 表现
    没有级别 调试信息和严重错误混在一起，看不出哪条该重视
    不能关 想在生产环境少打一点，只能去删 print 语句 ⚠
    转眼就没 控制台滚动几屏，出事现场已经消失
    没有出处 只知道有人打了这行，不知道是哪个模块打的

    logging 恰好把四个问题都解决了：

    能力 具体做法
    有级别 debug / info / warning / error / critical ✓
    能开关 改一个阈值，低于它的调用自动被丢掉 ✓
    能落盘 写进文件，事后还能翻 ✓
    带出处 格式化串里能打上模块名、函数名、行号 ✓

    8.2 五个级别与适用场景¶

    级别 数值 什么时候用 例子
    DEBUG 10 排查细节，平时关掉 变量的中间值、循环到第几轮
    INFO 20 正常运行的关键节点 「读入 300 条记录」「开始处理」✓
    WARNING 30 能继续，但值得知道 「第 2 条缺字段，已跳过」✓
    ERROR 40 这一步失败了 「数值无法解析成 float」
    CRITICAL 50 整体没法继续了 配置文件丢失、必需目录不存在

    级别是「数字越大越严重」，这一点值得亲眼看一下：

    问自己 答「是」就用

    判断依据： 「这件事之后程序还能不能继续」—— 能就 WARNING，这一步不行就 ERROR， 整体不行就 CRITICAL

    8.6 什么时候用 print、什么时候用 logging¶

    两者不是替代关系，是分工关系：

    场景 用哪个 为什么
    脚本的最终结果（给人看） print ✓ 这是程序的输出，不该被级别过滤掉
    命令行工具的正常输出 print ✓ 用户要看的就是它
    排查用的中间值 logging ✓ 交付时要能一键关掉
    需要保留证据的信息 logging ✓ 要落盘，事后能查
    库 / 模块内部 logging ✓ 库不该往用户屏幕上乱打印 ⚠

    最关键的一条判断：

    把 print 换成 logger，如果这句话在交付时「不需要出现」，就换对了
