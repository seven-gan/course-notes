    12 模块与包¶

    前面 11 页写的都是单个文件里的代码。可一旦程序变长，问题就来了：

    现象 后果
    一个文件几百上千行 找不到东西、改一处影响一片
    同一段代码在多个脚本里复制粘贴 改一处要改好几份，迟早漏掉
    想用别人写好的工具 不知道 import 背后发生了什么
    两个项目的依赖版本冲突 装了 A 的版本，B 就跑不起来

    这一页解决的就是这些：

    • 模块：把代码拆到多个文件
    • 包：把多个模块组织成目录
    • 虚拟环境：让不同项目的依赖互不干扰

    这一页的核心问题

    「我写的东西，怎么让别人（包括两周后的自己）能用上？」

    答案就三层：

    1
2
3
    一个文件          → 模块 module
一个目录（多个模块）→ 包 package
一套隔离的依赖     → 虚拟环境 virtual environment

    一、模块：一个 .py 文件就是一个模块¶

    假设你写了 mytools.py：

    # @file: mytools.py
"""我的工具模块（演示用）。"""

PI = 3.141592653589793


def circle_area(r):
    """圆的面积。"""
    return PI * r ** 2


def is_prime(n):
    """判断质数。"""
    if n < 2:
        return False
    for i in range(2, int(n ** 0.5) + 1):
        if n % i == 0:
            return False
    return True

    在同一个目录里就可以导入它：

    1
2
3
4
5
    import mytools

print("圆的面积:", round(mytools.circle_area(2), 4))
print("20 以内的质数:", [n for n in range(2, 21) if mytools.is_prime(n)])
print("模块里的常量 PI:", mytools.PI)

    圆的面积: 12.5664
20 以内的质数: [2, 3, 5, 7, 11, 13, 17, 19]
模块里的常量 PI: 3.141592653589793

    没有「安装」这一步 —— 只要文件在同一个目录，就能 import。 因为 Python 会把「当前脚本所在目录」加进搜索路径

    # @file: mytools.py 这行注释是什么意思

    它是本页为了让示例可运行而加的一个标注： 告诉读者（以及验证脚本）「这一段不是要执行的主程序， 而是要保存成 mytools.py 这个文件的内容」。

    你自己写的时候不需要这行注释 —— 只要把文件真的存成 mytools.py 就行

    二、import 的四种写法¶

    写法 用法 调用方式 建议
    import mytools 导入整个模块 mytools.circle_area(2) 推荐 ✓ 名字来源清楚
    import mytools as mt 导入并起别名 mt.circle_area(2) 名字太长时用 ✓
    from mytools import circle_area 只导入某个名字 circle_area(2) 只用一两个函数时用
    from mytools import * 导入全部公开名字 circle_area(2) 避免使用 ✗ 
    1
2
3
4
5
6
7
    import mytools as mt

from math import sqrt, pi

print("别名调用:", round(mt.circle_area(3), 4))
print("直接调用:", round(sqrt(16), 4))
print("导入的常量 pi:", round(pi, 6))

    别名调用: 28.2743
直接调用: 4.0
导入的常量 pi: 3.141593

    为什么不要用 from 模块 import *

    三个问题：

    问题 后果
    不知道名字从哪来 读代码时看不出 sqrt 是哪个模块的 ✗
    可能覆盖已有名字 同名函数被悄悄替换，很难查 ⚠
    污染命名空间 把模块里所有公开名字都塞进当前作用域

    示例：覆盖是无声的

     1
 2
 3
 4
 5

10
    from math import sqrt

print("先说一次 sqrt(16):", sqrt(16))


def sqrt(x):          # 自己定义一个同名函数
    return "我把 math.sqrt 覆盖了"


print("现在 sqrt(16) 是:", sqrt(16))


    先说一次 sqrt(16): 4.0
现在 sqrt(16) 是: 我把 math.sqrt 覆盖了

    第二次调用时 sqrt 已经是自定义的了 —— 这类覆盖在 import * 之后极难排查 ✗

    替代做法：明确写出要导入的名字，或用 import 模块 后加前缀

    别名为什么有用¶

    有些库的通行别名是社区约定，用它们能让代码更好读：

    1
2
3
4
5
6
    import math
import math as m

print("用别名 m.pi:", round(m.pi, 6))
print("等价于 math.pi:", round(math.pi, 6))
print("两者是同一个模块吗:", m is math)

    用别名 m.pi: 3.141593
等价于 math.pi: 3.141593
两者是同一个模块吗: True

    常见约定（在科学计算模块里会大量见到）：

    库 通行别名
    numpy np
    pandas pd
    matplotlib.pyplot plt

    看到 np.array(...) 就知道是 NumPy —— 这就是别名的价值

    三、导入时到底发生了什么¶

    理解这个过程，能解释很多奇怪现象

    当你写 import mytools，Python 会：

    步骤 做什么
    1 找：在搜索路径里找 mytools.py
    2 执行：把这个文件从头到尾执行一遍 ✓
    3 缓存：把结果存进 sys.modules
    4 绑定：让当前作用域的 mytools 指向这个模块对象

    关键点：模块在第一次被导入时会被完整执行一次， 之后再用 import mytools 就直接从缓存拿，不会重复执行

    用代码观察「只执行一次」¶

    1
2
3
4
    # @file: once.py
print("=== 我在被导入时执行了 ===")

VALUE = 42

    1
2
3
4
    import once
import once          # 第二次导入

print("VALUE =", once.VALUE)

    === 我在被导入时执行了 ===
VALUE = 42

    === 我在被导入时执行了 === 只打印了一次 —— 说明模块只执行了一次

    搜索路径 sys.path¶

    1
2
3
4
    import sys

print("搜索路径的条目数:", len(sys.path))
print("第一条是当前目录吗:", sys.path[0] in ("", ".") or len(sys.path[0]) == 0)

    搜索路径的条目数: 9
第一条是当前目录吗: False

    注意：sys.path 里的具体目录因机器而异， 所以上面只打印条目数这类稳定信息。

    搜索顺序（从前往后找，找到就用）：

    顺序 位置 说明
    1 当前目录 / 脚本所在目录 所以你自己的 mytools.py 能被找到 ✓
    2 PYTHONPATH 环境变量里的目录 手动指定的额外位置
    3 标准库目录 math、json 等
    4 第三方包目录 pip install 装的库

    ModuleNotFoundError 的三种原因与排查

    报错信息 原因 解决
    No module named 'mytools' 文件不在搜索路径里 确认两个文件在同一目录 ✓
    No module named 'numpy' 库没装，或装到了别的解释器 检查解释器；pip install numpy
    No module named 'pkg.sub' 包的路径不对 检查目录结构与 __init__.py

    第一类最常发生在：在别处运行脚本（比如在项目根目录运行 python sub/main.py，此时搜索路径加的是 sub/）。

    验证方法：在报错前打印一下路径信息

    1

    import sys
from pathlib import Path

print("当前工作目录存在吗:", Path.cwd().is_dir())
print("搜索路径条目数:", len(sys.path))
print("第一条是空串（表示当前目录）:", sys.path[0] == "")


    当前工作目录存在吗: True
搜索路径条目数: 9
第一条是空串（表示当前目录）: False

    四、if __name__ == "__main__": 到底在做什么¶

    这是 Python 里最好用、也最容易看懵的一行。先看现象：

     1

    # @file: counter.py
"""一个带自测代码的模块。"""


def count_up(n):
    """返回 1 到 n 的列表。"""
    return list(range(1, n + 1))


print("模块被加载了，__name__ =", __name__)

if __name__ == "__main__":
    print("这段只在「直接运行本文件」时执行")
    print("自测 count_up(3):", count_up(3))

    直接运行它（python counter.py）会看到两段都打印； 在别的文件里 import counter，就只有第一段打印

    1
2
3
4
5
    import counter

print("--- 现在是导入方在说话 ---")
print("导入后，counter.__name__ =", counter.__name__)
print("调用函数:", counter.count_up(4))

    模块被加载了，__name__ = counter
--- 现在是导入方在说话 ---
导入后，counter.__name__ = counter
调用函数: [1, 2, 3, 4]

    原理：__name__ 的值取决于「怎么用这个文件」

    使用方式 __name__ 的值 if 里的代码
    直接运行 python counter.py "__main__" 执行 ✓
    被导入 import counter "counter" 不执行 ✓

    所以这行的作用：把「自测代码」和「库代码」放在同一个文件里， 而导入时不会触发自测

    这是 Python 的标准写法，几乎所有正式模块都会写它。

    为什么必须这么写¶

    不写会怎样：别人 import 你的模块时， 你的自测代码会立刻执行 —— 打印一堆东西、跑一堆计算， 甚至可能因为依赖不存在而直接报错 ✗

     1

    # @file: bad_demo.py
"""反面示例：没有保护的自测代码。"""

import math


def area(r):
    return math.pi * r ** 2


# ⚠ 没有 if 保护：导入方会看到这行输出
print("我在导入时就打印了，这很不好")

    1

4
    import bad_demo

print("导入方只想用 area 函数")
print("面积:", round(bad_demo.area(1), 4))

    我在导入时就打印了，这很不好
导入方只想用 area 函数

    注意导入 bad_demo 的那一刻那行打印就出现了 —— 导入方完全没打算触发它 ✗

    正确写法：把测试代码放进 if __name__ == "__main__": 里

    相对导入（包内部互相引用）¶

    包里的模块要用同一个包里的其他模块时，用相对导入：

    写法 含义
    from . import utils 同一层目录下的 utils
    from .utils import helper 同层的 utils 里的 helper
    from .. import other 上一级包里的 other

    相对导入的两个常见错误

    错误 1：在「非包内」的文件里用相对导入 ✗

    1
2
    # @expect-error
from . import something


    ImportError: attempted relative import with no known parent package

    原因：这个文件不是包的一部分，没有「当前包」可参照。 相对导入只能在包内部的模块里用。

    错误 2：直接运行包内的模块

    假设 mycookbook/strings_util.py 里写了 from . import math_util， 然后你直接运行这个文件（python mycookbook/strings_util.py） —— 也会报类似的错。

    原因：直接运行时，Python 把这个文件当独立脚本看， 它不知道自己在哪个包里。

    正确做法：从包的上一层目录，以模块路径方式运行：

    python -m mycookbook.strings_util

    -m 表示「按模块路径运行」，这样 Python 才知道包结构

    七、虚拟环境：让项目之间互不干扰¶

    为什么需要它¶

    问题场景：项目 A 需要 NumPy 1.20，项目 B 需要 NumPy 1.26。

    做法 结果
    都装在同一个 Python 里 必然冲突：装了一个，另一个就不满足 ✗
    每个项目一个独立环境 各装各的，互不影响 ✓

    虚拟环境 = 一份独立的、属于某个项目的 Python 依赖目录。

    1

   ├── myenv_projectA/     ← 项目 A 的独立环境（NumPy 1.20）

    requirements.txt：把依赖记录下来¶

    问题：你装了 NumPy、pandas…… 但别人（或另一台机器）怎么知道要装什么？

    答案：把依赖写进 requirements.txt。

    生成的内容形如（这只是示意，实际版本号以你的环境为准）：

    1

    别人拿到项目后，一条命令装齐：

    freeze 与手写的取舍

    做法 优点 缺点
    pip freeze 精确复现环境 ✓ 会把间接依赖也写进去，列表很长
    手写主要依赖 简洁、意图清楚 ✓ 版本不锁死，可能装到新版本

    实践建议：

    • 做研究要可复现 → 用 pip freeze 或把关键库写死版本 ✓
    • 做工具/库 → 手写主要依赖，并给版本范围（如 numpy>=1.24）
    • pip freeze 生成的列表不要手改 —— 下次再 freeze 会覆盖

    写法对照：

    写法 含义
    numpy 任意版本
    numpy==1.26 锁定到具体版本（可复现）✓
    numpy>=1.24 至少 1.24
    numpy>=1.24,<2.0 区间（避免大版本不兼容）✓

    例题 3：为什么运行包内模块会失败¶

    下面结构里，calc.py 想用同包的 helpers.py，写了相对导入。 直接运行 python mypkg/calc.py 却报错。为什么？怎么改？

    1
2
3
4
    mypkg/
├── __init__.py
├── helpers.py
└── calc.py

    calc.py 的内容：

    1
2
3
4
5
    from . import helpers


def run():
    return helpers.double(21)
    思路

    「相对导入」要相对于谁？直接运行文件时，Python 知道它在哪个包里吗？

    解答

    原因：相对导入（from . import ...）的含义是 「从当前包的位置找」。但直接运行 python mypkg/calc.py 时， Python 把 calc.py 当成独立的顶层脚本， 它不属于任何包 → 没有「当前包」可参照 ✗

    两种修法：

    修法一（推荐）：用 -m 按模块路径运行

    # 在 mypkg 的「上一层」目录运行
python -m mypkg.calc

    这样 Python 才知道 mypkg 是包，calc 在包里

    修法二：改成绝对导入

    1
2
3
4
5
6
7
    # @file: mypkg/calc_abs.py
"""用绝对导入代替相对导入。"""
import mypkg.helpers as helpers      # 明确从包的最外层写起


def run():
    return helpers.double(21)

    对比两种导入方式：

    方式 写法 能否直接运行该文件
    绝对导入 import mypkg.helpers ✓ 可以（只要 mypkg 在搜索路径里）
    相对导入 from . import helpers ✗ 不行（必须用 -m 方式）

    实践建议：

    场景 用
    包要在多处被导入 绝对导入 ✓（更明确）
    包内部模块互相引用、且希望包名可改 相对导入 ✓
    想直接运行包内某个模块做调试 用 python -m 包.模块 ✓

    例题 4：虚拟环境的判断与排查¶

    某同学激活了虚拟环境、pip install pandas 也成功了， 但在编辑器里运行代码仍报 No module named 'pandas'。 请给出排查思路。

    思路

    终端的环境与编辑器用的解释器是两件独立的事。

    解答

    核心认识：「终端里激活了环境」不等于「编辑器用了那个环境」 ⚠

    五步排查：

    步骤 操作 期望结果
    1 在代码里打印 sys.executable 记住这个路径 A
    2 在已激活的终端里运行 python -c "import sys; print(sys.executable)" 得到路径 B
    3 比较 A 与 B 应当相同 ✓
    4 若不同 → 在编辑器里切换解释器 指向 .venv 里的 Python
    5 若相同却仍报错 → 在该终端 python -m pip install pandas 用模块方式重装

    解释器路径末尾两段: ('anaconda3', 'python.exe')
是否在虚拟环境里: False
pandas 可用，版本前缀: 2

    注意「是否在虚拟环境里」这一行（用 sys.prefix != sys.base_prefix 判断， 这是可靠的判据）：

    输出 含义 下一步
    是否在虚拟环境里: True 解释器正确 若 pandas 不可用 → 在该环境里 python -m pip install pandas
    是否在虚拟环境里: False 编辑器用的是全局 Python ✗ 切换解释器到 .venv ✓

    为什么推荐 python -m pip install：它保证 pip 装到 正在运行的这个解释器里，不会出现「pip 与 python 不是同一个」的问题

    Q4 python -m pip install xxx 与 pip install xxx 有什么区别？ 为什么推荐前者？

    提示

    想想「pip 命令」和「python 命令」可能指向不同的安装位置。

    解答

    区别：

    命令 用的 pip 装到哪
    pip install xxx 系统 PATH 里的 pip 不一定是你想用的那个环境 ⚠
    python -m pip install xxx 当前 python 自带的 pip 一定是这个 python 的环境 ✓

    为什么推荐 python -m pip：

    场景 pip install python -m pip install
    机器有多个 Python 可能装错地方 ✗ 明确装到你指定的那个 ✓
    虚拟环境已激活 通常没问题 一定没问题 ✓
    排查「装了却导入不到」 难定位 直接排除「装错环境」这个可能 ✓

    验证「pip 与 python 是否匹配」：

    小结¶

    要记住的 为什么
    一个 .py 文件就是一个模块 同目录即可 import，无需安装
    导入会执行模块一次，之后走缓存 所以顶层代码只在首次导入时跑
    import 模块 优于 from 模块 import * 名字来源清楚、不易覆盖
    if __name__ == "__main__": 让文件既能当库导入、又能直接运行 ✓
    包 = 目录 + __init__.py __init__.py 可以为空
    相对导入只能用于包内部 直接运行包内文件会失败，用 python -m
    标准库很丰富 先查标准库，再考虑装第三方
    虚拟环境隔离项目依赖 python -m venv .venv + 激活
    requirements.txt 记录依赖 别人一条命令就能复现环境
    python -m pip install 把 pip 与解释器绑死，避免装错地方 ✓
    .venv/ 不提交版本库 体积大、含本机路径、可重建
