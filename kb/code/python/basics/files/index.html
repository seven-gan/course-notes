    这一页解决一个问题：让数据「活过程序结束」，并且能安全地读回来。

    前面几页处理的数据都活在内存里：变量、列表、字典 —— 程序一退出，它们全部消失。 要保存结果、要读别人给的数据、要批量处理一批文件，就必须读写磁盘上的文件。

    问题是，写文件比 print 危险得多。下面这些行都不是「写错了语法」， 而是语法完全正确、后果却很严重：

    你可能会写出 你以为的结果 真实结果
    open(p, "w") 再写新内容 在文件末尾加上新内容 原文件内容被全部清空
    不写 encoding="utf-8" 与平时一样能读写中文 换了环境就读不出来，甚至报错
    f.write("第一行") 输出一行 两行内容粘在同一行
    "data" + "/" + name 拼路径 跨平台都能用 在 Windows 上很容易拼错
    写完 f.write(...) 不关闭 内容照样存下来了 可能只写了一半，或迟迟不落盘
    f.readlines() 读一个很大的文件 和逐行读一样 整个文件塞进内存，可能直接崩掉

    这一页的每一个结论后面都跟着一段可运行的代码和它的真实输出 —— 页面里所有 output 块都是实跑出来的，不是手写的。

    学完这一页，你将能够：

    能力 具体表现
    选对模式 知道该用 r / w / a / x 中的哪一个，知道 w 会清空、x 会报错
    安全地关文件 一律用 with，知道它在异常时也会自动关闭
    选对读法 小文件用 read()，大文件用逐行迭代，知道 readlines() 的内存代价
    写对换行 知道 write() 不加换行、writelines() 也不加，print(file=f) 才加
    不踩编码坑 知道为什么必须写 encoding="utf-8"，知道 utf-8-sig 与表格软件的关系
    用 pathlib 管路径 用 / 拼路径，用 name / suffix / parent 取信息，不再手工切字符串
    处理结构化数据 会用 csv 读表、用 json 读配置，知道 newline="" 与 ensure_ascii=False 的必要性
    不污染目录 做实验用 tempfile，写完删掉，项目目录始终干净

    这一页的主线

    本页按「读 → 写 → 路径」三条线展开，贯穿的判据只有一条：只要碰磁盘，就必须能安全地读回来。

    第二节先立规矩（模式与 with），第四到六节讲读、写与编码，第七节把路径统一到 pathlib， 最后两节处理 CSV 与 JSON 两种常见格式。其中「读」与「写」两条线各自独立，可以分开看。

    这页的重点

    最容易翻车的四点，先说在前面：

    陷阱 一句话提醒
    w 是「清空重写」不是「打开」 想追加必须用 a，w 会在打开的一瞬间删掉原内容
    永远写 encoding="utf-8" 不写就用「系统默认编码」，换台环境就可能乱码或报错
    write() 不加换行 要换行得自己写 "\n"，或用 print(..., file=f)
    拼路径用 pathlib，不要拼字符串 Path("a") / "b.txt" 会自动选对分隔符，字符串拼接不会

    另外记住一条排查口诀： 文件读不出来，先查三件事 —— 路径对不对、编码对不对、模式对不对。

    一、为什么把「文件与路径」单独作为一页¶

    1.1 内存与磁盘是两套世界¶

    程序运行时，数据放在内存里。内存有三个特点，正是它不适合存长期数据的原因：

    特点 含义 后果
    断电即失 内存需要持续供电 关机就没了
    进程独占 只有当前进程看得到 别的程序拿不到
    容量有限 比磁盘小得多 装不下大表、图片、日志

    磁盘解决这三个问题：掉电不丢、谁都能读到、容量大得多。 而文件就是操作系统给磁盘上的数据起的名字 —— 有了名字，别的程序才找得到它。

    1.2 但「文件」比「变量」多出了四件事¶

    变量只需要一个名字。文件需要同时说清楚四件事，缺一件就出错：

    要说清楚的 由谁决定 说错了会怎样
    位置（在哪个目录下） 路径 FileNotFoundError：根本找不到
    模式（读还是写、文本还是二进制） open() 的第二个参数 内容被清空、或读写报错
    编码（字节怎么变成文字） encoding= 参数 乱码、UnicodeDecodeError
    何时关闭 with 语句 内容没写完、文件被占用、资源泄漏

    这四件事没有一件是「写错语法」，全都能顺利跑起来，然后给你一个错的结果 —— 这正是文件操作比算术更容易出问题的原因。

    1.3 路径为什么单独值得讲¶

    路径看起来只是字符串，实际上它是操作系统之间的差异最集中的地方：

    差异 一种系统 另一种系统 直接拼字符串的后果
    目录分隔符 / \ 在另一种系统上拼错
    盘符 没有 有（C: 之类） 代码无法通用
    大小写 区分 通常不区分 测试通过、上线失败
    当前工作目录 都会变 都会变 相对路径指向的文件换了

    结论：路径不要用字符串拼，用 pathlib.Path。 它把「分隔符、盘符、父目录、扩展名」这些概念都做成了对象上的操作， 换操作系统不用改代码。这一页第七节会专门讲。

    2. 再往下看真实输出，对一下自己的猜测

    二、open() 的模式全表¶

    open() 的用法长这样：

    1

    三个参数里，模式与编码是最容易写错的。这一节先把模式讲透。

    2.1 模式字符串由三部分组成¶

    模式不是「一堆选项」，而是三个问题各回答一位：

    组成 回答的问题 可选值
    主模式（必选一位） 我要拿这个文件做什么？ r 读、w 写（清空）、a 追加、x 独占创建
    数据种类（可选） 我处理的是文字还是字节？ t 文本（默认）、b 二进制
    是否双向（可选） 同一个文件对象要既能读又能写吗？ 加一个 +

    所以 "r+b" 读作「读为主 + 可写 + 二进制」，"a+t" 读作「追加 + 可写 + 文本」。 顺序不影响含义，"rb+" 与 "r+b" 等价。

    2.2 四种主模式：这是最该背下来的一张表¶

    模式 中文名 文件不存在时 文件已存在时 打开后读写指针 能读吗 能写吗
    r 只读 报 FileNotFoundError 正常打开，内容保留 文件开头 能 不能
    w 只写（清空） 新建空文件 先把内容全部清空 文件开头 不能 能
    a 追加 新建空文件 内容保留 文件末尾 不能 能
    x 独占创建 新建空文件 报 FileExistsError 文件开头 不能 能

    记住三句话：

    1. r 最安全：它绝不会改动文件，文件不存在就直接报错。
    2. w 最危险：它不是「打开」而是「清空后打开」，打开的那一瞬间原内容就没了。
    3. x 最谨慎：它专门用于「只允许创建一次」的场景，比如写日志头、生成初版配置。

    下面这张表把三个「想改文件」的模式放在一起对比，差别一眼就能看出来：

    你的意图 该用 用错的后果

    三、必须用 with：为什么值得强制自己¶

    3.1 文件「关掉」到底在做什么¶

    open() 返回的不是「文件本身」，而是一个文件对象（file object）， 它背后握着操作系统分配的资源。close() 要把这些东西还回去：

    close() 做的事 不做的后果
    把缓冲区里没写完的数据刷到磁盘 你以为写好了，其实丢了
    释放操作系统里的文件句柄 句柄用完，后面 open 直接失败
    通知系统「这个文件我不用了」 别的程序无法改名、删除、移动它
    让 f.closed 变成 True 你可能对已关闭的文件再操作一次

    最容易被忽略的是第一条：写文件时，Python 并不会每写一个字符就落盘， 而是先攒在缓冲区里，够了再一次性写。关文件就是「最后一次强制落盘」。

    5.4 什么时候该 flush()¶

    写文件时数据先进入缓冲区，攒够了才真正落盘。这带来一个副作用：

    情形 现象
    程序正常结束 / with 正常退出 缓冲区会被自动刷新，内容完整
    程序被强制杀掉（崩溃、断电、任务被中断） 缓冲区里没落盘的部分会丢
    你正在盯另一个程序读这个文件 它可能暂时读不到刚写的内容

    判断依据：

    场景 要不要 flush()
    普通写文件、写完就关 不用，with 会处理
    要实时写日志、让别的程序马上看到 要，或直接用 flush=True 的 print
    长时间运行、希望崩溃时只丢很少的数据 要，定期 flush
    写一个几 KB 的配置文件 不用

    批量写文件的标准做法是「先在内存里攒好，最后一次性写」—— 这样既快又不会留下写了一半的文件：

    1
2
3

with open(p, "w", encoding="utf-8") as f:         # 再一次性写出去
    f.writelines(lines)

    六、编码：为什么必须写 encoding="utf-8"¶

    这一节是本页最重要的部分。文件操作里最「诡异」的故障， 绝大多数都出在编码上：内容明明写进去了，读出来却是一堆问号。

    6.1 字符、字节、编码的关系¶

    先把三个词分清楚：

    概念 是什么 例子
    字符 人能认的符号 「中」是一个字符
    字节 磁盘上真正存的东西，只能是 0 到 255 之间的数 0xE4 是一个字节
    编码 「字符 ↔ 字节」的对照规则 UTF-8 规定「中」写成三个字节

    一句话概括：文件里存的永远是字节，不是字符。 encoding 参数就是告诉 Python：「按哪本字典，把字节翻成字符」。

    Python 里的两个类型正好对应这两边：

    类型 是什么 用在哪
    str 字符序列，一个元素是一个字符 文本模式（默认）读写的都是它
    bytes 字节序列，一个元素是 0 到 255 的整数 二进制模式读写的是它

    两者之间的转换方法很直白：

    方法 方向 例子
    字符串.encode("utf-8") str → bytes "中".encode("utf-8") 得 b'\xe4\xb8\xad'
    字节串.decode("utf-8") bytes → str b'\xe4\xb8\xad'.decode("utf-8") 得 '中'

    6.3 不写 encoding 会怎样¶

    不写 encoding 不等于「用 UTF-8」，而是「用当前系统的默认编码」。 Windows 中文环境下的默认编码通常是 cp936（也就是 GBK 系）， Linux 与 macOS 近年来基本是 utf-8。

    这带来两个方向相反的坑：

    方向 现象
    别人给的文件是 UTF-8，你的程序按 GBK 读 乱码，或直接 UnicodeDecodeError
    你的程序按 GBK 写，别人按 UTF-8 读 对方乱码，或对方报错

    后果最轻的是「乱码」，最重的是「程序直接崩溃」。 两种都演示一下 —— 先制造一个 GBK 文件，再按 UTF-8 去读：

    6.4 结论：写死 encoding="utf-8"¶

    这一页最该带走的一条规则：

    1
2
    打开文本文件，一律显式写 encoding="utf-8"。
不要依赖系统默认编码，也不要靠「在我这儿能跑」来判断。

    理由只有一句：默认编码是环境决定的，而环境不是你能控制的。

    你写的代码 在一种环境 在另一种环境 结果
    open(p) 不写编码 默认 UTF-8，正常 默认 GBK，可能报错 同一份代码两种行为
    open(p, encoding="utf-8") 正常 正常 ✓ 行为固定

    好消息：pathlib 的 read_text / write_text 也是这个规则， 必须写 encoding="utf-8" 才稳。这一点和 open() 完全一致。

    还有一个更省事的做法：Python 3.7 之后支持 open() 的 errors 与编码组合， 而 3.15 起文本模式默认编码会变成 UTF-8。但在那之前，显式写 encoding 是唯一稳的做法 —— 而且显式写出来，读代码的人一眼就知道这个文件的编码约定。

    不写 encoding 的三种惨状，按严重程度排

    严重程度 现象 为什么难查
    轻 中文显示成问号或方块 你还看得出来「这里有问题」
    中 UnicodeDecodeError: 'utf-8' codec can't decode byte ... 报错信息只给你一个字节的位置，得回头找源头
    重 写出去的文件在别的环境里读不出来 本机一切正常，问题是别人遇到的

    最后一种最难查：代码在开发环境跑得好好的， 交付出去才出错，而错误现场不在你手里。

    所以判断依据是：

    场景 做法
    自己写完自己读 照样写 encoding="utf-8" —— 省得以后出问题
    文件要给别的程序、别的系统用 必须写，且最好约定统一用 UTF-8
    收到的文件编码确实不是 UTF-8（老资料、老系统导出的表） 先确认它的真实编码，再按那个编码读；读进来后自己另存为 UTF-8
    二进制文件（图片、压缩包） 用 b 模式，这时不需要 encoding

    6.5 utf-8-sig 与「表格软件打开中文乱码」¶

    问题场景：程序导出一份带中文的 CSV，用文本编辑器打开一切正常， 用表格软件双击打开，中文全变成乱码。

    原因不是文件写错了，而是缺了一个「签名」。 某些表格软件在打开 CSV 时不做编码探测， 直接按本机默认编码（Windows 中文环境下是 GBK 系）去解释字节； 而你的文件是 UTF-8，于是中文被按两字节一组误读，成了乱码。

    解决办法是在文件最开头写三个特殊字节 EF BB BF， 它叫 BOM（字节顺序标记）—— 它的唯一作用就是「告诉读的人：这是 UTF-8」。

    Python 为这个需求提供了现成的编码名：

    编码名 写入时 读取时
    "utf-8" 一个字节都不多写 只读内容
    "utf-8-sig" 开头多写 3 个字节的 BOM 读到 BOM 就自动去掉

    utf-8-sig 该用的和不该用的场合

    场合 用哪个 为什么
    导出 CSV，要交给表格软件打开 utf-8-sig 让那类软件知道这是 UTF-8
    程序之间交换数据（两个 Python 程序） utf-8 对方能自己指定编码，BOM 反而多出脏数据
    写 JSON utf-8 带 BOM 的 JSON 不是合法的 JSON，解析会失败
    读别人给的文件，不确定有没有 BOM utf-8-sig 有 BOM 就去掉，没有也不出错，两头都安全
    写配置文件、源代码 utf-8 大多数工具把 BOM 当多余内容

    一句判断口诀：「给表格软件看的文件用 utf-8-sig，其它一律 utf-8」。

    还有一个隐蔽的坑：如果读文件时用了 utf-8 而文件带 BOM， 第一个字符会是 \ufeff。这会导致「看起来一样的两个字符串不相等」：

    比较 结果 原因
    text == "ID" False 实际是 "\ufeffID"
    text.strip() == "ID" 仍然 False strip() 不会去掉 \ufeff
    text.lstrip("\ufeff") == "ID" True 手工去掉
    用 utf-8-sig 读 True ✓ 推荐：让读取时就处理掉

    最后一行是唯一省心的做法 —— 在打开文件的那一步解决，而不是在每一处比较前处理。

    七、pathlib.Path：推荐的路径处理方式¶

    7.1 为什么不要用字符串拼路径¶

    先看一段「看起来没问题」的代码：

    1
2
3
    base = "data"
name = "scores.csv"
full = base + "/" + name          # ✗ 手工拼

    它在本机也许跑得通，但埋了四个雷：

    雷 说明
    分隔符 有的系统用 /、有的用 \，写死一个就不通用
    多出来的斜杠 base 末尾本来有斜杠时，会拼出 data//scores.csv
    缺少规范化 data/../other/x.csv 这种写法不会被整理
    到处手写切字符串 想拿扩展名就得 name.split(".")[-1]，遇到 x.tar.gz 就错

    Path 把这些都做成了对象上的操作：拼路径用 /， 取信息用 .name / .suffix，列目录用 .iterdir()。

    需求 ✗ 字符串做法 ✓ Path 做法
    拼两个路径 a + "/" + b a / b
    取文件名 p.split("/")[-1] p.name
    取扩展名 p.split(".")[-1] p.suffix
    取所在目录 "/".join(p.split("/")[:-1]) p.parent
    判断是否存在 用 os.path 系列函数 p.exists()
    列目录下的文件 要写通配符再手工过滤 p.iterdir() / p.glob("*")
    读整个文件 open(...) + read() p.read_text()
    写整个文件 open(...) + write() + close() p.write_text(text)

    这样写还有一个好处：路径在打印和拼接时自动带上正确的分隔符， 在 Windows 上显示成 data\scores.csv，在别的系统上显示成 data/scores.csv， 而你的代码一个字都不用改。

    7.2 / 运算符：跨平台拼路径¶

    Path 重载了 /，所以拼路径的写法就是数学里的除号：

    写法 得到
    Path("data") / "scores.csv" data/scores.csv
    Path("data") / "sub" / "a.txt" data/sub/a.txt（可以连着写）
    Path("/tmp") / "a.txt" 绝对路径 + 相对路径
    Path("a") / Path("b/c.txt") 两边都可以是 Path

    注意 | 与 / 的对比：字符串用 / 是「把两个字符串接起来」， Path 用 / 是「子路径」—— 它会自动处理分隔符、去掉多余的斜杠， 并在右边是绝对路径时整体替换掉左边。

    八、二进制模式 b：什么时候必须用¶

    8.1 文本模式与二进制模式的根本区别¶

    b 模式与文本模式差的不是「怎么读」，而是「读出来是什么类型」：

    文本模式（r / w） 二进制模式（rb / wb）
    读出来 / 要写进去的类型 str（字符） bytes（字节）
    是否需要 encoding 需要，且应该显式写 不需要，不能写
    换行符 自动做平台转换 原样不动
    典型对象 文本文件、CSV、JSON、配置文件 图片、压缩包、音频、可执行文件

    为什么二进制模式不能写 encoding：因为 encoding 描述的是「字节 ↔ 字符」的翻译规则， 而二进制模式根本不做翻译 —— 它读到的就是磁盘上的原始字节。

    判断依据只有一条：这个文件的字节序列本身是数据，而不是「某种编码下的文字」。

    压缩包（.zip .gz） rb / wb 内容是压缩后的二进制流
    音频、视频 rb / wb 同上
    可执行文件、字体 rb / wb 二进制格式
    任意文件的无损复制 rb + wb 不需要知道它是什么，字节照抄就行
    文本、CSV、JSON r / w 需要按编码翻译成字符

    「用二进制模式复制任意文件」是 b 模式最常用的场景 —— 它对文件内容毫无假设。

    try:
        with open(src, encoding="utf-8") as f:
            f.read()
    except UnicodeDecodeError as e:
        print("用文本模式读:", type(e).__name__, "-", e)

    # 二进制文件里只能写字节
    try:
        with open(src, "wb") as f:
            f.write("文本")
    except TypeError as e:
        print("往二进制文件写字符串:", type(e).__name__, "-", e)

    # 二进制模式复制：字节照抄，不管内容是什么
    dst = d / "copy.bin"
    with open(src, "rb") as fin, open(dst, "wb") as fout:
        fout.write(fin.read())
    print("复制后字节完全相同:", src.read_bytes() == dst.read_bytes())

    写法 结果
    f.write(b"abc") 在二进制模式下 ✓ 正确
    f.write("abc") 在二进制模式下 ✗ TypeError，要先 "abc".encode("utf-8")
    f.write("abc") 在文本模式下 ✓ 正确
    f.write(b"abc") 在文本模式下 ✗ TypeError: write() argument must be str, not bytes
    "abc" + b"abc" ✗ TypeError，两种类型不能相加
    "中文".encode("utf-8") ✓ 得到 b'\xe4\xb8\xad\xe6\x96\x87'

    判断口诀：文本模式想「字节」→ bytes.decode()；二进制模式想「文字」→ str.encode()。 中间的转换只能显式做，Python 不会替你猜。

    12.3 大文件一次性载入爆内存¶

    这一条不容易在小例子中演示（演示它需要很大的文件）， 但它的机制很值得说清楚：

    写法 内存里同时存在多少内容
    f.read() 整个文件 + 一个字符串对象
    f.readlines() 整个文件 + 一个列表（每行一个对象）
    list(d.rglob("*")) 所有路径 + 一个列表
    for line in f: 一行
    for x in d.rglob("*"): 一个路径

    「一次性收集」的代价是可以算出来的： 一个字符在内存里不是一字节 —— 字符串对象有固定开销，列表每个元素也有开销。 所以 readlines() 常常比 read() 更费内存。

    判断依据：

    文件/目录规模 写法
    确定很小（几 KB 到几 MB） read() / readlines() / sorted(glob)，怎么方便怎么来
    可能很大（几十 MB 以上、行数上万） 逐行迭代，边读边处理
    要多次遍历同一批数据 先筛出需要的小部分再收集，别全收

    一个实用的习惯：处理大文件时， 不要先把数据都读进内存再开始处理，而是「读一行 → 处理一行 → 丢掉」。 需要保留的只是结果，不是过程数据。

    import tempfile
from pathlib import Path

with tempfile.TemporaryDirectory() as tmp:
    p = Path(tmp) / "numbers.txt"
    p.write_text("\n".join(str(i) for i in range(1, 101)) + "\n", encoding="utf-8")

    # ✗ 先全部读进内存，再统计
    lines = p.read_text(encoding="utf-8").splitlines()
    total_all = sum(int(x) for x in lines)
    print("一次性读入的行数:", len(lines), "总和:", total_all)

    # ✓ 边读边算，内存里始终只有一行
    count = 0
    total = 0
    largest = 0
    with open(p, encoding="utf-8") as f:
        for line in f:
            value = int(line)
            count += 1
            total += value
            largest = max(largest, value)
    print("逐行处理的行数:", count, "总和:", total, "最大值:", largest)
    print("两种写法的结果一致:", count == len(lines) and total == total_all)

    这段代码的模式值得记住： 「边读边算」的循环里，只维护你要的结果（计数、求和、最大值）， 而不是把读到的内容攒起来。 这样无论文件多大，内存占用都不变。

    三种写法的取舍：

    写法 内存里同时有几个「东西」 适合
    read() / read_text() 一个巨大的字符串 小文件、要整体处理
    readlines() 一个大字符串 + 每行一个对象 只在文件确实很小时用
    for line in f: 只有一行 ✓ 大文件的标准写法

    为什么 readlines() 比 read() 更费： 列表里每一个元素都是一个独立的字符串对象， 除了内容本身还有每个对象的固定开销。 行数越多，这部分开销越大 —— 一个千万行的文件， 光是「装行的容器」就能多占几百兆。

    推荐写法就是上面第二种：在循环里只维护你要的结果 （计数、求和、最大值），不保存读到的原始行。 这样文件多大，内存占用都不变。

    顺带回答「为什么逐行迭代能省内存」： 文件对象是一个迭代器，每次 next 只从缓冲区取一行。 这和你前面学过的「生成器是惰性的」是同一个机制 —— 用的时候才产生，用完就丢。

    判断依据，一句话： 「文件可能很大」是用逐行迭代的唯一充分理由， 而这个理由在你写代码的那一刻几乎总是成立的。

    为什么「直接写相对路径」可能找不到文件：

    关键事实 后果
    相对路径是相对当前工作目录的 换了工作目录，就指向别的文件
    工作目录由「怎么启动程序」决定 命令行、编辑器、别的脚本调用，三者可能不同
    文件本身没有变 所以你会觉得「明明是同一个文件」

    所以「找不到文件」最常见的三种原因是： 路径基准不对（相对路径）、编码不对（读成乱码）、模式不对（该读用了写）。 排查顺序也照这个来。

    小结¶

    要记住的 为什么
    主模式只有四种 r 读、w 清空写、a 追加、x 独占创建
    w 会清空已存在的文件 打开的一瞬间原内容就没了 —— 要保留旧内容必须用 a
    x 已存在就报错 防止误覆盖；「只在不存在时创建」就用它
    + 才既能读又能写 w / a 都不可读；r 不可写
    一律 with open(...) as f 异常时也会关闭；手动 close() 中间抛异常就漏掉了
    write() 不加换行 要换行自己写 "\n"，或用 print(..., file=f)
    write() 只收字符串 写数字要先转，f.write(92) 会 TypeError
    读出来自带换行符 readline / readlines / 逐行迭代的结果都带 \n
    逐行迭代最省内存 大文件用 for line in f，别用 readlines()
    必须写 encoding="utf-8" 不写就用系统默认编码，换环境就出问题
