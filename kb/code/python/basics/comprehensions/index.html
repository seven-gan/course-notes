    09 推导式与生成器¶

    这一页讲 Python 最有「个性」的一组语法。

    同样一件事，别人用五行循环写出来，Python 老手一行就写完了：

    1
2
3
4
5
6
7
8
9
    # 新手写法
squares = []
for x in range(1, 6):
    squares.append(x ** 2)

# 老手写法
squares = [x ** 2 for x in range(1, 6)]

print(squares)

    [1, 4, 9, 16, 25]

    第二种写法叫推导式（comprehension）。它不只是「短」， 更重要的是它把「从一堆数据造出另一堆数据」这个意图，直接写在了表达式的位置上 —— 读代码的人一眼就知道「这里是在做映射/筛选」，不用一行行去追循环里的细节。

    而生成器（generator）解决的是另一个问题：数据太多、装不进内存。 它把「一次算完」改成「用一个算一个」，代价是只能遍历一遍。

    这一页学完，你将能够：

    能力 具体表现
    写出四种推导式 列表、字典、集合、生成器表达式
    判断该用哪一种 按「要不要重复遍历」「数据多大」来选
    看懂 for 的底层 知道 iter() / next() / StopIteration 各自做什么
    用 yield 写生成器 处理大文件、无限序列、流水线
    知道什么时候不该用 能识别「看起来很酷其实更难读」的写法

    这页最容易搞错的一点

    推导式和生成器表达式长得像，行为完全不同。 列表推导式用 []，生成器表达式用 ()：

    写法 产出 能遍历几遍
    [x * 2 for x in data] 一个列表，数据已经在内存里 想遍历几遍都行
    (x * 2 for x in data) 一个生成器，数据还没算 只能遍历一遍 ✗

    括号一换，语义就变了 —— 后面会用实例证明这件事。

    一、为什么需要推导式¶

    1.1 先看不用的代价¶

    假设需求是：把一批成绩里及格的挑出来，换算成百分制。

    用「循环 + append」写：

    1
2
3
4
5
6
7
    # 需求：把 60 分以上的成绩换算成百分制（原始满分 80）
raw = [56, 72, 48, 79, 65, 30, 77, 61]
converted = []
for score in raw:
    if score >= 60:
        converted.append(score / 80 * 100)
print(converted)

    [90.0, 98.75, 81.25, 96.25, 76.25]

    同样的需求，用推导式写：

    1
2
3
    raw = [56, 72, 48, 79, 65, 30, 77, 61]
converted = [score / 80 * 100 for score in raw if score >= 60]
print(converted)

    [90.0, 98.75, 81.25, 96.25, 76.25]

    两段代码的输出完全一样，差别在于：

    维度 循环 + append 推导式
    行数 4 行 1 行 ✓
    要有几个变量 需要一个中间列表 converted 不用，结果直接是表达式的值 ✓
    读起来是什么 「先建空表，再循环，再判断，再追加」 「从 raw 里取满足条件的，换算成百分制」✓
    出错面 忘记 append、缩进错、把 if 写成嵌套 结构定死，写错就是语法错，跑不起来 ⚠
    速度 稍慢（每次都要查 append 方法） 稍快 ✓

    1.2 关键区别：推导式是「表达式」，循环是「语句」¶

    这一点比「短」重要得多：

    • 循环是语句 —— 它只能出现在某一行上，不能直接写在别的表达式里面。
    • 推导式是表达式 —— 它有值，所以可以：
    1
2
3
4
5
    # 推导式的值可以直接被别的函数用掉
raw = [56, 72, 48, 79]
print(sum(raw) / len(raw))                       # 先看平均数
print(sum(s for s in raw if s >= 60))            # 只把及格的加起来
print(max(s / 80 * 100 for s in raw))            # 换算后取最高分

    63.75
151
98.75

    用循环就写不出「直接塞进 sum(...) 里」这种结构 —— 你得先建一个列表、循环填满它，再传给 sum。

    一句话总结推导式的价值

    它把「造数据」的意图表达成了一个值，而不是一串步骤。

    代价是：一行里塞太多逻辑就没人看得懂了。 所以第六节专门讲「什么时候不该用」

    二、列表推导式¶

    2.1 最小形式：[表达式 for 变量 in 可迭代对象]¶

    结构可以这样拆：

    1
2
3

    def chunks(items, size):
    """把任意可迭代对象切成固定大小的小块。"""

    if buf:                 # 别漏掉最后不满的一块

    7.1 判断顺序：先问「要不要重复遍历」¶

    1

    │
    ├─ 是 ──→ 用容器：列表推导式 [] / 字典 {} / 集合 {}
    │
    └─ 否 ──→ 数据量是不是很大（百万级以上 / 未知长度 / 可能是无限）？
                 │
                 ├─ 是 ──→ 用生成器：表达式 () 或 yield 函数
                 │
                 └─ 否 ──→ 用列表推导式（更简单，速度也更稳）

    这把「要不要重复遍历」放在第一问，是有原因的： 它是唯一会让程序出错的差别（生成器第二次遍历就空了）。 而「内存」和「速度」只是效率问题，选错了顶多慢一点、占得多一点。

    7.2 决策速查表¶

    你的情况 用什么 原因
    结果要存下来、排序、取长度、取下标 列表推导式 ✓ 生成器没有 len、不能索引
    结果要反复遍历好几遍 列表推导式 ✓ 生成器第二遍就空了
    结果要按名字查 字典推导式 ✓ 直接建映射
    结果要去重 / 做集合运算 集合推导式 ✓ 顺带完成去重
    结果马上就会被 sum/max/any 吃掉 生成器表达式 ✓ 中间列表根本不必建
    数据上百万，只需过一遍 生成器表达式 ✓ 内存恒定
    数据可能是无限长 生成器函数 ✓ 列表装不下
    需要逐行读大文件 生成器函数 ✓ 内存只放一行
    需要多级处理流水线 生成器函数 ✓ 惰性、可组合
    逻辑超过两步、有分支判断 普通 for 循环 ✓ 可读性优先

    想省的是什么 用什么
    省代码行数 / 提升可读性 推导式 ✓
    省一点 CPU 时间 推导式（比循环快约 1.3 倍）✓
    省内存 生成器表达式 / 生成器函数 ✓
    省「后面的计算」 生成器 + islice / break ✓

    小结¶

    要记住的 为什么
    推导式是表达式，循环是语句 推导式的值能直接塞进 sum()、max() 里
    if 在 for 后是筛选，在 for 前是变换 前者会改变元素个数，后者不会
    多 for 推导式：外层在前、内层在后 顺序写反结果顺序就变了
    [] 是列表、{} 是字典/集合、() 是生成器 括号一换，语义就变
    {} 加冒号是字典，不加是集合 空 {} 永远是空字典，不是空集合
    生成器只能用一次 它不保存已产出的元素，第二遍就是空的
    要遍历第二遍就必须用容器 这是「选错了会出错」的唯一差别
    生成器省内存，不一定更快 体积和数据量无关，但每次取值都有开销
    sys.getsizeof 能直接证明内存差别 列表随元素增长，生成器恒定不动
    for 的底层是 iter() + next() + StopIteration 懂了它，所有「一次性」现象都能解释
    yield 让函数变成生成器，next 启动后才执行 惰性求值：不取就不算
    无限序列必须配刹车（islice / break） 否则死循环或内存耗尽
    有副作用（print、append）就用循环 推导式是为「造数据」设计的，不是为「做动作」
    多步逻辑、三层以上嵌套 → 回循环 可读性优先于「短」
    推导式的变量不泄漏（Python 3） 但也因此会遮蔽同名的外层变量
    筛选 = 造新列表，不要边遍历边删 边遍历边删会漏掉元素
    计时结果必须用 text 块 毫秒数在不同机器上一定不同
