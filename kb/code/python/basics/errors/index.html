    10 异常与调试¶

    这一页解决一个问题：让「出错」从「程序崩溃」变成「一条可读的信息 + 一个可控的决定」。

    前面九页写的代码，都建立在一个默认前提：一切都会按预期发生 —— 变量一定有值、列表一定不越界、用户一定输入数字、文件一定在那儿。

    真实情况几乎从不如此。Python 的做法不是「默默算出一个错的结果」， 而是立刻停下来，抛出一个带类型的异常对象，并附上完整的调用轨迹。 学会读这段轨迹、学会判断「谁该负责处理它」，就是这一页的全部内容。

    能力 具体表现
    分清两类错误 一眼判断是「语法错误」（程序根本没启动）还是「运行时异常」
    读懂报错 从 Traceback 读到最后一行，找到真正出错的位置
    认出常见异常 见到 KeyError、ValueError、AttributeError 就知道该查什么
    控制错误流向 用 try / except / else / finally 精确决定「出错之后做什么」
    主动暴露问题 用 raise 与 assert 让错误尽早出现，而不是带病继续跑
    定位疑难 bug 用 print 加 !r、断点调试、logging 三种手段看清中间量
    分辨反模式 认出 except: pass、用异常当流程控制、捕获过宽这三类坑

    这页最重要的三句话

    ① 报错信息是唯一免费的信息来源。

    初学者看到一屏报错的第一反应，往往是「赶紧让它别报错」， 于是写下 except: pass —— 结果把真正的 bug 一起藏了起来 ✗

    正确的第一反应是问三句：

    1
2
3
    1. 报的是哪一类异常？          → 类型说明「哪一类事情出了问题」
2. 最下面那个 File 指到哪一行？ → 那是真正出错的位置
3. 消息说我给了什么、它要什么？ → 消息通常写得很直白

    ② 要让错误尽早暴露，而不是尽早消失。

    ③ 只有「我知道该怎么办」的异常，才值得被捕获。

    一、错误分成两大类¶

    Python 遇到的错误分成两种情况，它们的处理方式完全不同。 先分清它们，才知道下一步该看哪儿。

    1.1 语法错误：程序根本没启动¶

    Python 执行一个文件分两步：先整体编译，再逐行执行。 只要编译不通过，一行代码都不会运行 —— 连第一句 print 都不会执行。

    先看一段正常代码作为对照：

    1
2
3
4
    total = 0
for i in range(5):
    total += i
print("循环跑完了，total =", total)

    循环跑完了，total = 10

    现在把 for 语句结尾的冒号删掉，并在最前面加一句 print：

    1
2
3
4
    # @expect-error
print("这一行有机会执行吗？")
for i in range(3)
    print(i)

    SyntaxError: expected ':'

    注意输出里没有「这一行有机会执行吗？」

    这一句本该在第一行就执行。它没出现，说明程序根本没启动 —— 编译阶段就把整个文件拦下了

    SyntaxError 一族的特点：

    特征 说明
    什么时候发现 运行之前，编译阶段
    已经执行了多少行 零行
    报错位置准不准 很准，还会指出这一行的哪个位置有问题
    能用 try 抓住吗 不能（下一小节演示）
    该怎么修 改代码，让它能编译通过

    1.2 异常：程序跑起来之后才出事¶

    第二类错误发生在运行过程中：代码本身写得没问题，编译也通过了， 但运行到某一行时它发现这件事做不到。

    1
2
3
4
5
6
    # @expect-error
print("第一行执行了")
values = [1, 2, 3]
print("第二行也执行了")
print(values[10])
print("这一行不会被执行")

    第一行执行了
第二行也执行了
IndexError: list index out of range

    对比上一段，这里能看到两句已经打印出来的信息 —— 说明程序真的跑起来了，只是跑到第 4 行时撞上了 IndexError（下标越界）， 于是第 5 行再也没有机会执行。

    这种「运行到某一刻才发现做不到」的情况，就叫异常（exception）。

    1.3 两类错误的对照表¶

    维度 语法错误（SyntaxError 一族） 异常（运行时）
    发现时机 运行之前（编译阶段） 运行到那一行时
    已经跑了多少 一行都没跑 跑到出错那一行
    典型例子 少冒号、少括号、引号没配对、缩进乱 KeyError、ValueError、ZeroDivisionError
    报错里有什么 文件名 + 行号 + 指位置的箭头 完整的调用轨迹 + 异常类型 + 消息
    能用 try 抓住吗 不能 能
    责任通常在哪 代码本身写错了 数据、环境、用户输入或代码逻辑
    修法 补语法 改逻辑，或主动处理这种意外

    try 抓不住语法错误

    很多人的直觉是「把可能出错的代码用 try 包起来就安全了」。 但语法错误发生在编译阶段，那时 try 还不存在：

    1
2
3
4
5
6
    # @expect-error
try:
    value = 1
except Exception:
    print("抓住了")
  print("这一行的缩进是 2 个空格")

    IndentationError: unindent does not match any outer indentation level

    程序根本没有走到 try，所以 except 里那句永远等不到执行 ✓

    判断依据： 报错是 SyntaxError / IndentationError 一族 → 不用想 try， 回去改代码；报错是别的异常 → 才轮到 try 出场。

    1.4 为什么要有「异常」这套机制¶

    设想另一种设计：出错就返回一个特殊值（比如 -1 或 None）。那会带来三个麻烦：

    麻烦 说明
    信息不够 -1 说不出「是哪个键不存在」；异常对象带类型、消息，还能带自定义属性
    容易被忽略 返回值可以不管；异常不会自己消失，除非你显式捕获
    调用链丢失 返回值只说「这一步失败了」；异常会告诉你「从哪儿一路走到这一步」

    所以 Python 的选择是： 错误必须携带信息，而且必须被处理，或者继续往上抛。

    2.2 most recent call last 到底在说什么¶

    这句话的字面意思是「最近的一次调用在最后」。 换句话说，Traceback 是按时间顺序从上往下排的：

    1

   ↓

    所以阅读规则是：从下往上读。

    1
2

    第 1 步：看最后一行「异常类型 + 消息」   → 发生了什么
第 2 步：看它上面最近的 File 行          → 在哪一行、哪个函数
第 3 步：再往上，看是谁调用了它          → 这条调用链是怎么走过来的

    为什么必须「从下往上读」

    如果从上往下读，最先看到的是入口那一帧（<module>）。

    而入口那一帧往往完全正确 —— 它只是发起了调用，本身没有任何毛病。 盯着它看，你什么也修不了 ✗

    真正的答案永远在最下面那一帧：那里才是「做不到」发生的地方 ✓

    import re
import traceback


def clean_trace(text):
    """去掉新版 Python 才有的细粒度定位行（由 ^ / ~ 组成），使输出稳定。"""
    keep = []
    for line in text.splitlines():
        if line.strip() and set(line.strip()) <= {"^", "~"}:
            continue
        keep.append(line)
    return "\n".join(keep)


def inner(x):
    return 10 / x               # 出事点在这里


def middle(x):
    return inner(x) + 1


def outer(x):
    return middle(x) * 2

except ZeroDivisionError:
    info = traceback.format_exc()

print(re.sub(r'File "[^"]*"', 'File "script.py"', clean_trace(info)))

    第 3 帧 middle 里的 return inner(x) + 1 又把参数原样传给 inner

    2.4 读报错的固定四问¶

    把这套动作固定成四个问题，遇到任何报错都按顺序问一遍：

    顺序 问自己 去哪儿看
    1 是什么异常？ 最后一行的冒号前面
    2 消息说了什么？ 最后一行的冒号后面
    3 真正出错在哪一行代码？ 最下面那个 File 行，以及它下面的源代码行
    4 调用链从哪儿来？ 从最上面一帧往下看，参数是怎样传进来的

    只看最后一行不够，只看最上面一行更糟

    两种典型的误读：

    误读方式 后果
    只看最后一行「KeyError: 'count'」 知道缺了 count 键，但不知道是哪一步的数据缺的
    只看第一帧「错在模块顶层」 那一帧只是入口，它本身没写错，改了也没用 ✗

    力气应该花在中间那几帧上：它们显示数据是怎样一层层传下去的， 又在哪一层变得不符合预期

    8.2 断点调试：让程序停下来让你看¶

    print 的替代方案是在代码里打一个断点（breakpoint）—— 程序运行到那一行时暂停，把控制权交给你。

    在编辑器里的典型操作（各编辑器按钮位置不同，名称基本一致）：

    操作 常见快捷键 做什么
    打 / 取消断点 在行号左边点一下（出现红点） 标记「运行到这一行时暂停」
    开始调试 F5 启动程序并运行到第一个断点
    单步跳过 F10 执行当前行；遇到函数调用不进去
    单步进入 F11 执行当前行；遇到函数调用就进去
    单步跳出 Shift+F11 从当前函数返回上一层
    继续 F5 一直跑到下一个断点或程序结束
    停止 Shift+F5 结束这次调试

    暂停时你能看到什么（这是断点相对 print 的核心优势）：

    面板 内容 有什么用
    变量（Variables） 当前作用域里的所有变量及其值 不用猜该打印谁，全都摆出来了 ✓
    调用栈（Call Stack） 从入口到当前的每一层函数 直接对应 Traceback 的帧，还能逐层查看各层的局部变量 ✓
    监视（Watch） 你手动加进去的表达式 盯一个复杂表达式，每步都重新求值 ✓
    控制台（Console） 暂停时可以输入表达式求值 现场试 len(x)、type(y)、x[0]

    三种单步该怎么选：

    当前行的内容是 用哪个
    普通赋值、运算、print F10 单步跳过 ✓
    调用你自己写的函数，想进去看 F11 单步进入 ✓
    已经在某个函数里，想快速回到调用方 Shift+F11 单步跳出 ✓
    调用的是标准库/第三方库 F10 —— 进到库里面通常没有意义 ✗

    断点用得好，关键是「先推断再验证」

    不要一上来就打一堆断点。有效的顺序是：

    步骤 做什么
    1 根据代码逻辑推断「问题应该出在哪个函数」
    2 只在那个函数入口打一个断点
    3 跑到之后，先看变量面板里各参数是不是你以为的值
    4 用 F10 一行行往下走，看哪一行之后值开始不对
    5 找到「值第一次变错」的那一行 —— 那就是真正的 bug ✓

    第三步是最容易被跳过、也最省事的一步： 很多 bug 在函数入口就已经是错的（参数传错了）， 再往里单步就白走了。

    9.1 在程序最外层装一个「总兜底」¶

    traceback 最典型的用法之一，是在程序入口装一层兜底：

    十一、什么时候该用 try，什么时候该让它崩¶

    11.1 判据表¶

    问自己 答「是」→ 用 try / except 答「是」→ 让它崩
    这个错误经常发生吗？ 会（用户输入、脏数据、网络抖动）✓ 几乎不会（说明是 bug）
    我知道该怎么处理吗？ 知道（跳过 / 重试 / 用默认值）✓ 不知道，只能往上抛
    处理后结果是正确的吗？ 是（跳过脏行，剩下的统计没错）✓ 否（只能掩盖，结果依然错）
    出错的位置离我近吗？ 就在这几行里 ✓ 在很远的调用链深处
    这是外部数据吗？ 是（文件、接口、用户输入）✓ 否（是我自己算出来的内部值）
    出错是不是说明我写错了？ 否 ✓ 是 —— 让它崩，别盖住 bug ✗

    11.4 一条总原则¶

    1
    好代码让错误尽早暴露 —— 而且暴露在最接近现场的地方。

    为什么「尽早」这么重要：

    错误暴露的时机 排查代价
    就在出错的那一行 看一条 Traceback 就懂了 ✓
    三百行之后，以一个莫名其妙的结果出现 要倒推很久 ✗
    上线三个月后，在客户的数据上 已经来不及了 ✗✗

    所以三件事按优先级排：

    优先级 做法
    1 不要用 except: pass —— 那是最彻底的「延迟暴露」
    2 用具体异常类型 —— 让 except 只拦下你真正预判的那一类
    3 在函数入口校验输入 —— 让错误在最靠近现场的地方被点名 ✓

    把这一页压缩成一张卡片

    看到什么 做什么
    SyntaxError / IndentationError 别想 try，回去改代码
    一屏 Traceback 从下往上读，先看最后一行
    想加 except 先问「我知道该怎么处理吗」
    想写 except: pass 几乎总是错的，至少记一条日志
    想写 except Exception 问「它会不会把代码 bug 也吞了」
    多个 except 从窄到宽排，Exception 放最后
    要换异常类型 raise NewError(...) from exc ✓

    错误分两类：语法错误与异常 语法错误程序根本没启动，try 抓不住，只能改代码
    Traceback 从下往上读 most recent call last：最下面那帧才是真正出错的位置 ✓
    上面几帧是调用链 它们告诉你数据从哪儿来，通常不是要改的地方
    IndexError 消息弱、KeyError 消息强 前者不告诉你有几个元素，后者把缺的键打出来 ✓
    TypeError 是类型不对，ValueError 是值不对 一句话分清：「种类不对」vs「种类对但值不行」
    try / else / finally 各有分工 else 只在没出错时执行；finally 无条件执行 ✓
    finally 里不要写 return 它会覆盖之前决定的返回值 ✗
    能用 with 就别手写 finally 忘记写 finally 不报错，只会悄悄泄漏资源
    except 从窄到宽排 顺序错了不报错，只是后面的分支全部失效 ✗
    裸 except: 连中断键都抓 后果是按中断键也停不下来
    只写 raise 才是原样重抛 写 raise e 会削弱原始现场信息
    换异常类型要带 from raise NewError(...) from exc 保留因果链 ✓
    自定义异常必须 super().__init__(消息) 否则 str(e) 是空串、e.args 是空元组 ✗
    assert 会被 -O 删掉 所以绝不能用它做输入校验，要用 if + raise ✓
    assert 给自己看，if + raise 给调用方看 前者是便签，后者是合同
    调试加标记要用 !r 只有 repr 能显示引号、空格、换行、全角字符 ✓
    print 加五个以上就换断点 断点的变量面板能看到全部状态，不用猜该打印谁
    logging 用 %s 占位，别用 f-string 消息被级别过滤掉时，占位写法一次格式化都不做 ✓
    logging 要输出到文件再读回 避免污染程序自己的标准输出
    traceback.format_exc() 只在 except 里用 它取的是「当前正在处理的异常」的完整轨迹
    完整 Traceback 只给日志，人话才给用户 路径和函数名对使用者是噪音
    except: pass 几乎总是错的 它把错误删了，而且不报错 ✗
    不用异常做正常流程控制 异常是给「意外」用的；「找不到」是常态，用普通判断
    捕获过宽会把代码 bug 一起吞了 症状是「结果不对但程序不报错」，最难查 ✗
    try 要尽可能窄 包 20 行，出错时分不清是哪一行
    数据不是我给的 → 处理；是我自己弄的 → 让它崩 这是「该不该 try」最快的判据 ✓
    好代码让错误尽早暴露 暴露得越早，排查代价越小

    一句话收束： 异常不是敌人，「不知道发生了什么」才是。 把这页的判据用熟之后，你写的程序会有一个明显变化 —— 出错的时候，它说的信息足够让你直接动手修。
