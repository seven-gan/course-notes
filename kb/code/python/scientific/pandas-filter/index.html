    06 筛选与变换¶

    这一页解决一个问题：拿到一张表之后，怎么把它「挑出需要的行」并「改成想要的样子」。

    真实的数据工作里，读进一张表只是起点。接下来你几乎一定会做这几件事：

    • 挑行——只留下成绩及格的学生、只看某几个城市的订单、排除测试数据；
    • 改列——把分数换成等级、把编码换成中文名称、把越界的值截断回来；
    • 排序——看看最高的前几名是谁、按城市再按成绩排一遍；
    • 分箱——把连续的分数切成「优秀 / 良好 / 中等」这样的档位。

    这四件事占据了日常数据处理的大部分时间。而且它们有一个共同特点： 写法看起来都对，结果却可能悄悄不对。 and 与 &、 括号的有无、inplace 与链式调用—— 这些都是「代码不报错、数字就是错的」的典型来源，本页会逐个演示。

    学完这一页，你将能够：

    能力 具体表现
    挑行 用布尔索引、isin、between、str.contains 写出准确的条件
    组条件 稳用 & / \| / ~ 并每次都给条件加括号，不被优先级坑
    写条件 在布尔索引与 query() 之间按场景选择，会用 @变量名 引用外部值
    排序 一次指定多列、每列不同升降序，并说清缺失值排在哪
    排名 用 rank 的四种 method 处理并列，知道每种给出什么名次
    造列 用整列算术、clip、np.where 做向量化派生，避免逐行 apply
    映射 分清 map（元素级）与 replace（值替换），用字典批量换标签
    分箱 用 cut 按自定义边界、qcut 按分位数等频，并用 labels 命名
    避坑 认出 SettingWithCopyWarning 的成因，用 .loc 或 .copy() 一次写对

    这页最容易搞错的三件事

    看起来差不多 实际差别 后果
    and / or 与 & / \| 前者要一个真假值，后者做逐元素运算 直接报 truth value of a Series is ambiguous
    A > 1 & B < 3 与 (A > 1) & (B < 3) 比较运算符优先级高于 & 不报错，但掩码完全不对，选出错误的行
    筛选后直接赋值 与 .loc 一步到位 前者在「切片副本」上写入 赋值可能不生效，还发 SettingWithCopyWarning

    第一件会报错，好抓；第二件静默出错，最难抓；第三件不报错也不生效。 本页会把三种情况都现场跑一遍，让你见过它们长什么样

    import pandas as pd

    细节 说明 什么时候会咬到你
    结果只有被选中的行 没被选中的行整行丢掉，不是变成空值 想保留全部行、只把不符合的标成缺失时，该用 where 而不是筛选
    索引保留原编号、不重排 上例留下的是 2, 3, 5 这类原索引 之后用位置序号去取数据时会对不上；需要干净序号就补一句 reset_index(drop=True)

    2.2 坑一：每个条件都必须加括号¶

    这是最危险的一个 —— 因为它不一定报错。

    Python 的优先级顺序是：算术 > 比较（> < ==） > 位运算（& | ^） > 逻辑（and or）。 所以当你写：

    1
    students["score"] > 60 & students["city"].notna()

    Python 并不是按你读的顺序去算的，而是先算 &：

    1
    students["score"] > ( 60 & students["city"].notna() )

    也就是说，它把 60 当成了一个「只有一位的掩码」去和后面的条件做按位与， 再把结果拿去和分数比较 —— 算出来的是完全不同的东西。 下面把它完整跑一遍，你会看到它不报错、但选出 6 行（全部）。

    7.3 把 apply 换成向量化：一份判据表¶

    apply 的代价是「放弃向量化」：它只能一行行（或一列列）去调用 Python 函数， 数据量大时可能比向量化写法慢几十倍。绝大多数 apply 都能被替换掉 —— 下面这份对应关系可以直接照抄：

    你想做的事 慢写法（apply） 快写法（向量化）
    整列加减乘除 df["a"].apply(lambda x: x * 2) df["a"] * 2
    两个列相加 df.apply(lambda r: r["a"] + r["b"], axis=1) df["a"] + df["b"]
    条件赋值（二选一） df["a"].apply(lambda x: "高" if x > 5 else "低") np.where(df["a"] > 5, "高", "低")
    条件赋值（多档） 多分支 apply 嵌套 np.where 或 pd.cut
    按区间分档 df["a"].apply(lambda x: 档位函数(x)) pd.cut(df["a"], bins=[...], labels=[...])
    一列的极差 / 均值 df.apply(lambda c: c.max() - c.min()) df.max() - df.min()
    取绝对值 / 截断 df["a"].apply(np.abs) df["a"].abs() 或 df["a"].clip(...)
    字符串大小写 df["s"].apply(lambda x: x.upper()) df["s"].str.upper()
    编码转标签 df["c"].apply(lambda x: 表[x]) df["c"].map(表)
    逐行调外部接口 / 读写文件 —— 只能用 apply（有副作用时无法向量化）⚠

    先试向量化，实在不行才上 apply

    顺序建议：

    1. 能不能用算术 / 比较直接算？（df["a"] * df["b"]）
    2. 能不能用 np.where / pd.cut / .str / .map 表达？（见上表）
    3. 都不行 —— 而且这行逻辑确实依赖整行的多个列 —— 才上 apply(axis=1)。

    另有一个必查项：apply 的返回类型是由函数返回值推断出来的。 函数里只要有一条分支返回字符串、另一条返回数字， 整列就会变成 object 类型，后续运算既慢又容易出错。

    11.2 为什么会这样：pandas 不知道返回的是视图还是副本¶

    base[base["a"] > 1] 这个操作，pandas 有两种做法：

    做法 含义 代价
    返回视图（view） 与父表共用同一块内存，改它 = 改父表 省内存、快，但语义危险
    返回副本（copy） 新开一块内存，改它 = 只改自己 安全，但要复制数据、费内存

    pandas 无法总是确定该用哪一种（取决于内部内存布局）， 于是它选择了「先用副本，但如果你改它，就警告你一声」这个折中方案。 警告不是 bug，而是它在说：「你这次的写入行为，我无法保证符合你的预期。」

    最坑的一种写法：链式赋值看起来像生效了，其实丢了

    比新增列更隐蔽的是链式赋值（在一条链的末尾赋值）：

    11.4 三行代码对照表¶

    意图 写法 结果
    改原表中满足条件的行 df.loc[条件, "列"] = 值 写入生效、无警告 ✓
    改筛选出来的子集 sub = df[条件].copy() 然后 sub["列"] = 值 只改子集、无警告 ✓
    改子集但忘了 .copy() df[条件]["列"] = 值 警告 ⚠，原表不变（赋值被丢掉）
    先筛选再新增列 sub = df[条件] 然后 sub["新列"] = 值 警告 ⚠，子集与父表关系不确定

    一条能省掉大量调试时间的规则

    只要一次操作里同时出现「筛选」和「赋值」，就把它改写成 .loc[条件, 列] = 值。

    # 陷阱 症状 怎么发现 正确做法

    小结¶

    要记住的 为什么
    布尔索引 = 用一个真假序列去挑行 比较运算返回 bool 的 Series，下标与原表一一对应 ✓
    筛选返回的是子集，索引保留原编号 需要干净序号时补 reset_index(drop=True) ✓
    多条件用 & / \| / ~，绝不用 and / or / not 前者逐元素运算，后者要求单个真值，会抛 Series is ambiguous ⚠
    每个条件都必须加括号 比较运算符优先级高于 &，漏括号静默算错 ⚠⚠
    掩码算完就打印行数 这是唯一能当场发现漏括号的办法 ✓
    布尔序列要长度一致或索引可对齐 否则报 Item wrong length 或 Unalignable boolean Series ⚠
    isin 判断集合归属，between 默认闭区间 两者都比手写比较更短、意图更清楚 ✓
    between 闭区间，cut 左开右闭 方向相反，混用会让边界值一个算、一个不算 ⚠
    NaN 不满足任何比较 想保留缺失行必须写 \| x.isna() ✓
    str.contains 用于筛选一律 na=False 否则掩码里混进缺失，报 Cannot mask with non-boolean array ⚠
    str.contains 默认按正则，case 默认区分大小写 搜字面量写 regex=False，需要忽略大小写写 case=False ✓
    query() 里可用 and / or，还支持 @变量名 阈值来自外部时写 query("x >= @thr")，不必拼字符串 ✓
    条件少用布尔索引，条件多用 query 各自的长处不同，混着用最舒服 ✓
    sort_values 支持多列，ascending 可传列表 写 ascending=False 会让所有列都降序 ⚠
    na_position 独立于 ascending 升降序换了，缺失值仍按 na_position 摆 ✓
    rank 默认 average，还默认升序 分数、成绩这类「越大越好」的场景必须写 ascending=False ⚠
    并列的四种处理：average / min / max / first min 给「并列第一」，first 给唯一名次 ✓
    「几个人」用 head，「第几名」用 rank 「名次 <= 3」在有并列时会给不止 3 行 ⚠
    整列运算不写循环 df["a"] * 0.06 一行顶一个 for，而且快得多 ✓
    clip 会改写数值，记得记录改动行数 改动比例偏高说明数据有系统性问题，该查原因而非抹平 ⚠
    np.where 做条件赋值，从最严格的条件往下嵌套 顺序反了会把高档次的条件吞掉 ⚠
    apply(axis=0) 按列、apply(axis=1) 按行 axis 默认是 0；用「函数里能不能直接写列名」可以验证方向 ✓
    优先向量化，apply 是最后选择 判据表里的九种替代写法能覆盖绝大多数场景 ✓
    apply 的返回类型不确定 混用字符串与数字会让整列变成 object，务必打印 dtype 确认 ⚠
    map 漏键会变缺失，replace 保留原值 换标签时 map 的缺失正好当「映射表完整性」检查器 ✓
    map 只能作用于 Series，replace 可以整表用 想一次改全表的多处脏值，用 replace ✓
    cut 按自定义边界，qcut 按分位数等频 「60 分及格」类是 cut，「把人群等分」类是 qcut ✓
    cut 记得 include_lowest=True 并给上界留余量 否则边界上的值会变 NaN，总人数对不上 ⚠
    分箱后第一件事是用 value_counts 数人数 边界设错会立刻暴露 ✓
    筛选后赋值：一律 .loc[条件, 列] = 值 一步到位，不踩 SettingWithCopyWarning，也逼你把意图写清 ✓
    在筛选结果上新增列：先 .copy() 同时想清「改原表还是改副本」，这两件事目标不同 ⚠
    inplace=True 返回 None，与链式调用冲突 用 df = df.method(...) 语义最清晰 ✓
    不报错不等于做对了 本页的坑里，只有两个会报错，其余全是静默出错 ⚠
