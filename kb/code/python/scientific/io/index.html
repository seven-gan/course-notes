    09 数据读写¶

    这一页解决一个问题：把「磁盘上的东西」变成「内存里的 DataFrame」，再把它安全地送回去。

    前面的页面里，数据都是我们自己用 pd.DataFrame({...}) 手搓出来的。 现实中的第一步不是搓数据，而是把别人给你的文件读进来： 老师发的成绩表是 Excel，导出的日志是 CSV，接口返回的是 JSON， 抓下来的样本越来越大，又得换成 Parquet。

    这一步失败的方式还特别隐蔽：程序不报错，数字却不等于你以为的那个数。 「007」变成 7、日期变成字符串、中文变成问号—— 这些都不会抛异常，只会让你在第三周的分析里得出错误结论。

    学完这一页，你将能够：

    能力 具体表现
    选格式 拿到一个需求就知道该写 CSV、Excel、JSON 还是 Parquet
    读得对 用 dtype / parse_dates / na_values 把类型钉死在读入那一刻
    存得住 知道什么时候必须 index=False，什么时候必须 utf-8-sig
    扛得住 文件比内存大时，用 chunksize 分块算完
    查得快 读完 30 秒内用一张检查清单确认「读进来的就是我以为的」

    这页最值得先记住的四条

    1. 读入的那一刻就要把类型定下来。 靠 pandas 猜，一定会猜到「猜错但你不知道」的那一天。
    2. 写 CSV 如果不加 index=False，会多出一列无名索引——读回来就叫 Unnamed: 0。
    3. 要给 Excel 打开的中文 CSV，编码必须写 utf-8-sig，不是 utf-8。
    4. 能用 Parquet 就别用 CSV：Parquet 的体积更小，而且能把 dtype 原样存回来。

from pathlib import Path

import pandas as pd

df = pd.DataFrame({
    "姓名": ["阿黎", "小北", "老周"],
    "分数": [88, 92, 75],
    "日期": pd.to_datetime(["2024-09-01", "2024-09-01", "2025-02-24"]),
})

with tempfile.TemporaryDirectory() as td:
    d = Path(td)
    df.to_csv(d / "a.csv", index=False, encoding="utf-8-sig")
    df.to_excel(d / "a.xlsx", index=False)
    df.to_json(d / "a.json", orient="records", force_ascii=False,
               date_format="iso")
    df.to_parquet(d / "a.parquet", index=False)
    print("四个文件都已写出:",
          all((d / n).exists() for n in ("a.csv", "a.xlsx", "a.json", "a.parquet")))

    back = {
        "CSV": pd.read_csv(d / "a.csv", parse_dates=["日期"]),
        "Excel": pd.read_excel(d / "a.xlsx"),
        "JSON": pd.read_json(d / "a.json", convert_dates=["日期"]),
        "Parquet": pd.read_parquet(d / "a.parquet"),
    }
    print(f"{'格式':<8}{'形状':<10}{'分数类型':<12}{'日期类型'}")
    for name, frame in back.items():
        print(f"{name:<8}{str(frame.shape):<10}{str(frame['分数'].dtype):<12}"
              f"{frame['日期'].dtype}")
    print("四种格式读回的行数一致:",
          len({len(f) for f in back.values()}) == 1)
    print("JSON 文件开头:", (d / "a.json").read_text(encoding="utf-8")[:30])

    维度 CSV Excel JSON Parquet
    典型场景 导出、日志、数据交换的「通用货币」 和人对表格、交作业、多工作表 接口返回、配置文件、嵌套结构 大数据中转、长期存储、列存储
    文本还是二进制 纯文本 二进制（本质是 zip 包） 纯文本 二进制
    体积 大 大（比 CSV 更臃肿，含样式开销） 最大（每个值都带键名） 最小，且可压缩
    能否保留类型 ✗ 几乎全丢，读回靠推断 部分保留（数字与日期格式） 部分保留（数字/布尔/字符串） ✓ dtype 原样保留
    读写速度 中等（要解析文本） 最慢（要开 Excel 引擎） 中等偏慢 最快
    依赖库 无（pandas 自带） 需要 openpyxl（写 .xlsx） 无 需要 pyarrow 或 fastparquet
    适合人工查看 ✓ 最适合，记事本就能开 ✓ 最适合，还有格式和公式 勉强可读，嵌套深了没法看 ✗ 完全看不懂
    能否分块读 ✓ chunksize ✗ ✗ ✓ 天然按行组读
    一句话定位 图「谁都能打开」 图「人能编辑」 图「程序之间说话」 图「快和省地方」

    把 Excel 当成「数据存储格式」是常见的选择错误

    Excel 文件读写慢、体积大、还容易被手工改动（有人加了表头装饰行、 有人合并了单元格、有人把数字设成文本），它适合作为「人对人的交付物」， 不适合作为「程序对程序的中间存储」。 如果一份数据每天要读 20 次，把它另存一份 Parquet，不要反复读 Excel。

    看清楚发生了什么：不加 index=False 时，pandas 会把行号当成一列写进去， 而且那一列没有名字——所以读回来时 pandas 只能给它起个名字叫 Unnamed: 0。

    to_csv 的常用参数一览：

    参数 作用 什么时候必须写
    index=False 不写行号列 几乎每次都写，除非索引本身就是数据
    encoding 输出的字符编码 要给人用 Excel 打开时写 utf-8-sig
    columns=[...] 只写指定列、并控制顺序 列的顺序有意义，或要丢掉中间计算列时
    float_format="%.2f" 浮点数保留几位 交出去的数字不能带一长串小数尾巴时
    na_rep="NULL" 缺失值写成什么 下游系统要求特定缺失标记时
    sep="\t" 换分隔符 值里本来就有逗号，又不想加大引号时
    compression="gzip" 边写边压缩 文件很大又要用 CSV 交换时

    2.2 编码详解：utf-8 / utf-8-sig / gbk¶

    这是中文用户绕不过去的一节。先把三个词拆开：

    • utf-8：把 Unicode 字符编成 1~4 个字节。中文一般占 3 字节。 它是事实上的国际通用编码，但没有「声明自己是什么编码」的机制。
    • utf-8-sig：先写 3 个字节的字节顺序标记（BOM） EF BB BF， 再写正常的 UTF-8 内容。这 3 个字节等于在文件开头插了一面小旗子： 「我是 UTF-8」。sig 就是 signature（签名）的意思。
    • gbk：中文 Windows 的老牌编码，中文占 2 字节。 大量国产软件、老系统导出的 CSV 都是它。

    问题就出在：Excel 打开一个没有 BOM 的 UTF-8 CSV 时，默认按系统本地编码（中文环境是 GBK）去解， 于是三个字节被强行当成 1.5 个汉字，屏幕上就是「阿鏍」「锟斤拷」这类乱码。 加上 BOM 之后，Excel 认得这面旗子，就会正确按 UTF-8 解，中文正常显示。

    BOM 造成的 bug 只在「列名比较」时暴露

    最常见的现场是：df["姓名"] 报 KeyError: '姓名'， 但你把列名打印出来看，明明写着「姓名」。 原因就是列名实际是 '\ufeff姓名'。 排查动作只有一个：打印 repr(df.columns[0])，让隐形字符现形。

    三个编码的对照：

    编码 中文占几字节 带 BOM Excel 直接双击打开中文 什么时候用
    utf-8 3 无 ✗ 乱码 程序之间传递、写 JSON、上 Linux 服务器
    utf-8-sig 3 ✓ 有 ✓ 正常 给 Excel 打开的中文 CSV 一律用它
    gbk 2 无 ✓ 正常 对接老系统；读别人给的老文件时

    一张「必须用 dtype=str 读」的清单

    字段类型 为什么不能当数字 写错的具体后果
    学号 / 工号 常带前导零 007 变 7，名单匹配全失败
    身份证号 18 位，超过 int64 精度 末几位被悄悄改动
    电话号码 有前导零，也可能有 + 0755... 变 ``，或整体变 float
    邮编 / 行政区划码 6 位带前导零 010000 变 10000
    版本号 / 班级号 本质是标签 1.10 被当浮点数，小于 1.9

    读入时统一写 dtype={"学号": "str"}， 比事后 df["学号"].str.zfill(7) 补救可靠得多。

import pandas as pd

df = pd.DataFrame({"姓名": ["阿黎", "小北", "老周"], "分数": [88, 92, 75]})

    四种 orient 的差别，看这张表就清楚了：

    orient 写出来的形状 行列信息在哪 什么时候用
    records [{列: 值, ...}, ...] 每行一个对象，列名重复出现 最常用，接口和前端都认这个
    columns {列: {索引: 值}} 列名在外层 按列取数据方便
    index {索引: {列: 值}} 索引在外层 索引有意义（如按学号组织）时
    values [[值, 值], ...] 完全没有 体积最小，但读回来列名变成 0, 1

    注意 values 的读回列名是 0 和 1—— 列名丢了，这就是「省到最小也丢了信息」的代价。

    默认 orient 是 "columns"。要传给别的系统时，请显式写 orient="records"， 因为它是最像「一张表」的形状，别人不用看文档就能懂。

    五、Parquet：该换掉 CSV 的时候¶

    Parquet 是列式存储格式。CSV 按行存，Parquet 按列存。 这个差别带来三个直接好处：

    特点 为什么有用

    自带压缩 默认就压缩，体积通常只有 CSV 的几分之一

    Q2 至少三种原因：

    原因 检查方法 修法
    一列里混进了非数字（如 未知、-、待补） df["分数"][pd.to_numeric(df["分数"], errors="coerce").isna()] 找出捣乱的值 na_values=[...] 声明成缺失

    整列本来就是空字符串 df["分数"].eq("").sum() na_values=[""]

    核心手法就一句： pd.to_numeric(..., errors="coerce") 之后是 NaN 的位置， 就是那些「不是数字」的格子——把它们揪出来看一眼，原因立刻就清楚了。

    Q3 三种情形的成因与修法：

    情形 成因 修法
    ① 抛 UnicodeDecodeError 编码猜错了。文件其实是 GBK 之类，却按 UTF-8 解，字节解不出来 依次试 encoding="gbk"、"utf-8-sig"、"utf-8"；能报错其实是好事，它至少告诉你不对
    ② 不报错但全乱码 编码「猜错但恰好能解码」，或者写文件时就没指定编码 找到原始文件真正的编码；写文件的一方统一规定用 utf-8-sig
    ③ 列名对不上 文件带 BOM，第一列名实际是 '\ufeff姓名' 用 encoding="utf-8-sig" 读（它会吃掉 BOM）

    第③种最隐蔽，因为它不报错也不乱码。 排查动作只有一个：打印列名的 repr， 让 \ufeff 这样的隐形字符自己现形。

    Q4 甲对，乙错。

    乙的错误在于：均值是不可加的。 它把每块的平均值当成同等权重的数据点去做平均， 等价于假设「每块的行数都一样」。 实际文件里块的大小通常一样（只有最后一块可能不满）， 所以乙的错往往很轻微，甚至看不出来—— 正因为如此它更危险：数据量分布一变，结果就悄悄偏了。

    甲的写法把「总和」与「人数」分开累加，最后相除， 天然带上了加权，任何块大小分布都正确。

    判断口诀：

    1
2
    可累加（直接相加就对）：总数、个数、最大值、最小值、总和
不可累加（要拆成分子/分母）：平均、比例、比率、方差、标准差

    遇到「不可累加」的统计量，就把公式展开成「分子累加 + 分母累加」， 最后再算一次。
